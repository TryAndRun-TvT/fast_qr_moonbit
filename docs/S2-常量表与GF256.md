### 3. 各交付物设计要点

#### 3.1 `internal/constants/capacity.mbt`（B2，叶节点）
对应 `version.rs` 中与「版本选择/容量/矩阵元数据」相关的部分：

| 交付 | 语义 | 参考锚点 |
|------|------|---------|
| 容量查询 `capacity(version, mode, ecl) -> Int` | 按 (序号, 模式序号, ECL 序号) 返回容量（比特/字节）| `version.rs:96` const fn `get` |
| `max_bytes(version, ecl) -> Int` | 该 (版本, ECL) 总数据字节上限（S1 推迟的 `from_version` 依赖它）| `version.rs` |
| 矩阵元数据 `information` / `alignment_patterns_grid` | 版本信息字、对齐图案网格坐标（供 S4 图案层）| `version.rs` 同名方法 |
| `size(version)` / `missing_bits` 等 | 边长与容量相关辅助 | `version.rs` |

> 依赖规则：**叶节点无依赖**，只提供以 `Int` 序号入参的查表函数，不 import lib（公共枚举
> 以序号传入，layout 文档 §4 边界约束）。S3 encode 会消费 capacity；S4 消费 alignment 网格。

#### 3.2 `internal/constants/hardcode.mbt`（B3，叶节点）
对应 `hardcode.rs`（B3）：

| 交付 | 语义 | 参考锚点 |
|------|------|---------|
| `ecc_to_groups(version, ecl) -> ...` | 分组信息；Rust 用 `(count<<24)|(size<<16)|...` 打进 u32，解码取回 | `hardcode.rs:14` |
| 格式信息表 / 版本信息 | 掩码择优后写真实 Format（S4/S5 用）| `hardcode.rs` |
| `get_polynomial(ec_index) -> ...` | 生成多项式（长度即纠错码字数，≤30）供 division 查表 | `hardcode.rs:324` |

> 依赖规则：叶节点，供 reedsolomon / matrix 查表。

#### 3.3 `internal/reedsolomon/reedsolomon.mbt`（B4，→ constants）
对应 `polynomials.rs`（B4），是本阶段唯一带算法的一环：

| 交付 | 语义 | 参考锚点 |
|------|------|---------|
| `LOG` / `ANTILOG`（[u8;255] 常量）| GF(256) 幂/对数查表 | `polynomials.rs:11-42` |
| `division(data, generator) -> [u8;255]` | 域除法取余（纠错码字）；查表 + 异或 | `polynomials.rs:83` |
| `structure(data, ecl, version) -> [u8;5430]` | 分块纠错 + 数据/纠错码字交织 | `polynomials.rs:106` |

**关键语义（照抄，framework §五.8 / gf256 概念文档）**：
- 除法：数据右对齐放 `[0;255]`，对每个非零首项 `alpha=ANTILOG[首项]`，逐生成项 `^= LOG[(by[j]+alpha)%255]`；余数即尾部 `generator.len()-1` 字节。
- 交织：数据区**逐块跨字节**、纠错区**逐字节跨块**（方向相反）；纠错区索引
  `start_error_idx + j*groups_total + i`。
- 上限常量：`MAX_ERROR=30`、`MAX_GROUP_COUNT=81`、`MAX_DATABITS=3000`、`structure` 固定 5430。
- 表驱动：所有域运算查表，禁止运行时算 alpha 幂。
- `% 255` 加法无负数场景，仍建议加越界断言（roadmap §3.2）。

> 依赖规则：仅 → `internal/constants`（取分组/生成多项式），不 import lib；ecl/version 以序号入参。

### 3. 源码核对：2 处需修正 + 3 张旁路表补充

> 逐文件核对 `/tmp/fast_qr/src/{version,hardcode,polynomials}.rs`，对照 [S2 方案] §3 的交付描述。

#### 3.1 【修正】capacity 的真正形态是 `Version::get`（最小版本选择），不是「反查容量」
- **方案 §3.1 描述**：`capacity(version, mode, ecl) -> Int`「按 (版本, 模式, ECL) 返回容量比特/字节」。
- **源码实际**（`version.rs:96` `Version::get(mode, ecl, len)`）：按 3 模式 × 4 ECL 展开为**长度分段
  阈值 → 返回最小可用版本**（如 Numeric-L：`0..=41 => V01`、`42..=77 => V02`…），共 480 段判断。
- **对 S3 encode 的意义**：encode 自动选版本用的是 `Version::get(mode,ecl,len)`——给输入长度找
  最小版本。故 capacity.mbt 必须落**「(模式,ECL,len) → 版本号」的分段阈值表**，而不是反查表。
  建议以「40 版本 × 4 ECL × 3 模式的单版本容量上限表」存储，`get` 做线性/二分查最小可用版本
  （等价于展开源码的 480 段判断，量级相同）。
- **可合并交付**：`max_bytes`（40 一维）实为「容量表中 ECL 无关的数据总字节上限」，与 `Version::get`
  的 Byte 模式一列数据同源但**语义不同**（`max_bytes` = 总数据字节上限，供 `from_version` 定缓冲）。

#### 3.2 【修正】`get_polynomial` 入参是 `(version, ecl)`，返回 31 条之一
- **方案 §3.2/3.3 描述**：`get_polynomial(ec_index)`（按纠错码字数索引）。
- **源码实际**（`hardcode.rs:324`）：`get_polynomial(version, ecl) -> &'static [u8]`，在 **31 条
  生成多项式**里按 `(version, ecl)` match 选出 1 条（如 `(V01,L)=&[0,87,229,…,21]`、度 7）。
  31 条 = 度 0..30；黄金常量在 `tests/polynomials.rs::GENERATOR_POLYNOMIALS: [&[u8];31]`
  （index = 长度 - 1）。
- **实现建议**：hardcode.mbt 存两张表——`GENERATOR_POLYNOMIALS[31]`（31 条生成多项式字面量）+ 
  `polynomial_index_for[(version,ecl)] -> 0..30`（160 项选择索引），对外暴露
  `get_polynomial(version_idx, ecl_idx) -> Array[Byte]`（等价源码语义）。绝不可只按 ec_index 建表。

#### 3.3 【补充】3 张旁路表：`data_codewords` / `data_bits` / `cci_bits`
方案未点名，但 **reedsolomon 的 structure 与 encode 都必需**，应一并纳入 S2 表集合：
| 函数 | 源码位置 | 语义 | S2 谁用 |
|------|---------|------|---------|
| `data_codewords(version,ecl)` | `hardcode.rs:263`（4×40 表）| 数据码字数（纠错区起点 `start_error_idx`）| reedsolomon `structure` 必须 |
| `data_bits(version,ecl)` | `hardcode.rs:297` | = `data_codewords*8` | encode 容量判定 |
| `cci_bits(version,mode)` | `hardcode.rs:302` | 字符计数指示符位数（随版本档变化）| encode 段头（S3）|
> 归属建议：`data_codewords`/`data_bits` 与容量强相关 → `capacity.mbt`；
> `cci_bits` 属编码信息 → 可放 `capacity.mbt`（与 mode 序号相关）或留 S3 encode 时再落。
> reedsolomon 只依赖 `data_codewords` + `get_polynomial` + `ecc_to_groups`。

### 2. 落地要点与决策

#### 2.1 capacity：按「(mode,ecl,len) → 最小版本」存容量上限表（修正后形态）
评估记录 §3.1 修正：capacity 真正形态是 `Version::get(mode,ecl,len)` 的**分段阈值选最小版本**，
非反查容量。实现据此把源码 **480 段判断展开为 `capacity_table[mode][ecl][version]` 单版本容量
上限**，`version_for(mode_idx,ecl_idx,len)` 线性扫最小可容纳版本（len 超 V40 → -1）。
- 表值从 `src/version.rs` `Version::get` 的 `min..=max => Vxx` 上限提取（脚本）；
- `max_bytes[40]`/`information[40]`/`alignment_grid[40]`/`missing_bits[40]` 亦脚本提取；
- `data_codewords[4][40]`（含派生 `data_bits`）随 capacity 落地（评估 §3.3），供 reedsolomon。

#### 2.2 hardcode：`ecc_to_groups` 解码为四元组、`get_polynomial` 用「生成多项式 + (version,ecl) 选择索引」
- `ecc_to_groups`：源码以 `u32` 位打包 `(count<<24)|(size<<16)|(count2<<8)|size2`，实现直接存解码后
  四元组 `(g1c,g1s,g2c,g2s)`，语义等价（评估 §3.4 已核实）；
- `get_polynomial(version_idx,ecl_idx)`：评估 §3.2 修正——不是按 ec_index，而是从 31 条生成多项式中按
  `(version,ecl)` 选 1 条。实现存 `generator_polys[31]`（度 = 索引）+ `generator_index[ecl][version]`
  （**由 `(max_bytes - data_codewords) / 分组总数` 求得 = 每块纠错码字数 = 度**，与源码 match 分组
  完全一致，规避了源码分组字面量的脆弱解析）；
- `format_information[4][8]`（纠错×掩码 → 15 位字）一并落地（S5 写真实 Format 用，非 S2 算法必须）。

#### 2.3 reedsolomon：照抄 polynomials.rs 语义（division 右对齐 + structure 双向交织）
- `LOG`/`ANTILOG` 各 256 项脚本提取；
- `division(data, by)`：右对齐入 255 字节工作区，对非零首项查 `ANTILOG` 得指数 alpha，逐生成项
  `LOG[(by[j]+alpha)%255]` 异或；返回尾部 `by.len()-1` 余数字节（等价 Rust 返回 `[0;255]` 后取尾）；
- `structure`：g1/g2 分块 division → 纠错区 `start_error_idx + j*groups_total + i` 逐字节跨块写入，
  数据区从 `push_idx=0` 逐块跨字节前插。返回 5430 字节缓冲（对齐 Rust 固定上限）；
- 依赖方向 `reedsolomon → constants`（moon.pkg 声明 `import`，声明的 `@constants` 已全部使用）。

#### 2.4 from_version 回填
`CompactQR::from_version(version_idx) = from_bits(@constants.max_bytes(version_idx) * 8)`，
等价参考 `compact.rs::from_version`（初始容量 = max_bytes×8 比特）。为让 from_bits/max_bytes 语义
一致，实现在 bitstream 侧新增对 constants 的依赖（此前 bitstream 为纯叶、无依赖）。

### 5. 偏离与说明
- **生成多项式选择用「度推导」而非源码 match 字面量分组解析**：源码 `get_polynomial` 用 `(Vxx|Vyy…,ECL)`
  多行分组，解析脆弱易错（曾误得 V40-L→度 7）。改由
  `度 = (max_bytes - data_codewords) / 分组总数` 直接推导，全 160 项为整数且与源码一致（V01-L=7、
  V40-L=30、V40-H=30 抽验吻合）。
- `ecc_to_groups` 存储解码后四元组（非 u32 原值），避免 32 位 Int 移位溢出歧义，语义不变。
- MoonBit 数组切片无内建 `sub_array`：reedsolomon 内加私有 `slice(data,from,to)` 助手。

当前 `moon.mod` 声明 `supported_targets = "+wasm+wasm-gc+js"`（含 js），CI 脚本三后端回归。

### 2. 已确认正确的设计点（维持现状）

| 决策 / 实现 | 评审结论 |
|-------------|---------|
| 大表一律由提取脚本从参考源码生成（禁止手抄铁律） | 铁律正确；脚本从 `version.rs`/`hardcode.rs`/`polynomials.rs` 展开，规避人工抄错 ✓ |
| `capacity` 采用「单版本容量上限表 + `version_for` 线性扫最小可容纳版本」 | 等价展开源码 480 段判断；线性扫 40 次、每次一次查表，encode 每段调用一次量级可忽略 ✓ |
| `ecc_to_groups` 存解码后四元组而非 u32 位打包 | 规避 32 位 Int 移位溢出歧义，语义等价 ✓ |
| `get_polynomial` 用「31 条生成多项式 + `generator_index[v][e]` 选索引」而非源码 match 分组解析 | 规避源码分组字面量脆弱解析；索引由 `(max_bytes-data_codewords)/分组总数` 求得 ✓ |
| `reedsolomon` 依赖方向 `constants（叶）→ reedsolomon` 单向无环 | 符合 internal 无环约束；声明的 `@constants` 全部使用，无 `unused_package` ✓ |
| `division` 右对齐入 255 工作区 + `structure` 双向交织 | `tests/structure.rs` 黄金（message 62 + error 72 字节）逐字节零偏差，最强正确性锚点 ✓ |
| `LOG/ANTILOG` 查表、`% 255` 取指数 | 域运算全查表，对齐性能决策；黄金验证无越界 ✓ |
| `version_for` / `capacity_bytes` 越界「静默回退」策略 | internal 受控调用方（测试/S3 encode），fast_qr 用 `None/Result`、此处回退不抛，属可接受 API 取舍（记录为注意点，非 bug）|
| `CompactQR::from_version(v) = from_bits(max_bytes(v)*8)` | 语义对齐 fast_qr（初始容量 = 版本码字总容量），容量不足由 `push` 按需扩容，非限制性（§3.4）|

### 3. 本次评审的动作

#### 3.1 【落地·决策】移除 `js` 后端（工程收敛）
- **背景**：S2 及更早分析把 `js` 作为「npm / 浏览器直出通道」候选纳入 `supported_targets`、
  CI 三后端回归与 README。但本项目现阶段与可预见的交付均以 **wasm 产物**为目标（`wasm-gc` 主推、
  `wasm` WASI 兜底），无真实 npm/js 分发需求。
- **动作**：将 `moon.mod` 的 `supported_targets` 由 `"+wasm+wasm-gc+js"` **收敛为
  `"+wasm+wasm-gc"`**；同步移除：
  - `scripts/build-and-run.sh` 的 js 回归（for 循环 `wasm-gc wasm js` → `wasm-gc wasm`，注释更新）；
  - `.cnb.yml` 多后端注释的 `+ js`；
  - `AGENTS.md` §3 后端声明与 §4 收尾命令、`README.md` 功能特性 / 编译章节 / 产物表 / 代码树注释。
- **验证**：`moon build lib --target js` 现返回
  `Package ... does not support target backend 'js'. Supported backends: [wasm, wasm-gc]`；
  `wasm-gc` / `wasm` 双后端 build+run+test 全绿。CI 脚本已同步，无 js 残留调用。
- **意义**：缩小支持面 → 减少未来维护（js 后端产物、`/*.js` 分发、node 宿主测试均无需再跟）。

#### 3.2 【落地·加固】表间不变量交叉一致性白盒测试
- **动机**：S2 交付物是**多张彼此应自洽的表**（容量表 / data_codewords / ecc_to_groups /
  generator_index / 生成多项式）。虽由脚本生成，但任何「日后手改单张表」或「脚本再生成时漏同步」
  都可能只让**单表测试**通过而破坏**跨表一致性**（现有黄金只抽查单表值/结构黄金，未断言跨表关系）。
- **新增**（`constants_wbtest.mbt`，测试 42→43）`table_cross_consistency_160`，对全 4×40 项断言：
  1. **分组自洽**：`g1c*g1s + g2c*g2s == data_codewords(e,v)`；
  2. **度自洽**：`(max_bytes(v) − data_codewords(e,v)) % (g1c+g2c) == 0`，且
     `get_polynomial(v,e).length() − 1 == (max_bytes−data_codewords)/(g1c+g2c)`
     （等价 `generator_index` 选表与分组、容量表互不漂移）；
  3. **容量最小性**：对每个 (mode,ecl) 抽 len∈0..100 断 `version_for` 返回的版本容量 ≥ len、
     且前一版本容量 < len（最小性），并核 `capacity_bytes` 相邻版本上界。
- **验证**：三后端全绿；该测试是本评审中实际验证过的核心自洽性证据（设计时先于代码用脚本核对
  V01/V10 抽验一致，落成断言后 160 项全过）。

#### 3.3 【落地·注释修正】`max_bytes` 语义易误导
- **问题**：`capacity.mbt` 中 `max_bytes_table`/`max_bytes()` 注释写「每版本**数据总字节上限
  （不含纠错）」，但其值（V1=26、V40=3706）实为 **ISO 该版本码字位置总容量（= 数据码字区 +
  纠错码字区合计）**——否则 V1-L 数据仅 19、不会等于 26。`CompactQR::from_version` 正是用它在
  编码缓冲里同时容纳「数据段 + 尾部纠错」，语义上是**版本总码字容量**而非某 ECL 的数据字节上限
  （数据字节上限应查 `capacity_table`/`data_codewords`）。
- **修正**：将 `capacity.mbt` 两处 + `bitbuffer.mbt::from_version` 注释改为明确表述「码字位置总
  字节容量 / 供 encode 定缓冲起步上界」，并在 `from_version` 补充「push 按需扩容、非限制」说明。
  纯注释改动，不触碰表值与逻辑（`.mbti` 无变化）。

#### 3.4 【记录·待 S3 复核】`from_version` 语义依赖 encode 收尾路径
- `from_version` 是否与 fast_qr 的 `compact.rs` 完全等价，本会话参考源码不可得（`/tmp/fast_qr`
  已随环境消失），仅按 fast_qr 文档语义推断「初始容量 = 版本码字总容量」。真正判等需 S3 encode
  消费它时对照 `tests/compact.rs` 黄金确认数据段/填充/终止符写入后的缓冲形态。
- 属记录项，非阻塞（push 会扩容，容量多寡不影响正确性、只影响预留）。

#### 3.5 【记录·性能观察】`structure` 固定 5430 字节缓冲
- `structure` 每次分配 5430 字节（对齐 Rust `[0;5430]` 上限），但多数版本实际只用前
  `data_codewords + 纠错字节`（V40 才接近 3706）。对齐参考是刻意取舍，正确性优先。
- 建议：S7 真正产码/封装时若测到分配热点，可改为「按实际 data_codewords+EC 长度分配 + 返回裁剪
  长度」，属后续优化，非本阶段阻塞。
