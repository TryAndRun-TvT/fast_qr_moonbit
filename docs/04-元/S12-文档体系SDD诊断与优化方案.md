## 1. 方法与口径（可复跑）

本文所有数字由以下命令产出（**递归，勿用 `docs/*.md`**——中文文件名与子目录都会漏）：

```bash
# ① 规模
git ls-files '*.md' | wc -l
git ls-files -z '*.md' | xargs -0 wc -l | tail -1

# ② 结构：标题统计（H1..H4）与重复 H2
git ls-files -z 'docs/*.md' | xargs -0 grep -hE '^#{1,4} ' | awk '{print length($1)}' | sort | uniq -c
git ls-files -z 'docs/*.md' | xargs -0 grep -h '^## ' | sort | uniq -c | sort -rn | head

# ③ 状态字段覆盖
git ls-files -z '*.md' | xargs -0 grep -lZ '⚠️' | tr '\0' '\n' | wc -l

# ④ 数字漂移（同一计数出现篇数）
for n in 146 147; do printf '%s: ' "$n"; git ls-files -z '*.md' | xargs -0 grep -lZ "$n" | tr '\0' '\n' | wc -l; done
export PATH="$HOME/.moon/bin:$PATH"; moon test | tail -1

# ⑤ 门禁现状（4 项）
bash scripts/docs-link-check.sh && bash scripts/test-scale.sh && bash scripts/publish-check.sh
```

**口径纪律**（与 [S11 §1](../02-证据/S11-无效代码与冗余文档清理评估.md) 一致）：
数字**只作量级参考**，不参与任何门禁；判定结论必须能由上面命令**机械复核**。

## 2. SDD 最佳实践调研（外部一手来源 + 本项目适配判定）

### 2.1 采样来源与结论

| # | 来源 | 核心主张 | 对本项目的适用性判定 |
|:-:|------|---------|---------------------|
| 1 | **GitHub Spec Kit**（`spec-driven.md`、`README.md`，2026 实读） | ① 「**权力反转**」：规格是主产物，代码是其表达（`specs` 驱动而非代码驱动）；② 五阶段工作流 `constitution → specify → plan → tasks → implement`；③ **规格必须可执行/无歧义**——否则无法生成可用系统；④ `[NEEDS CLARIFICATION]` 标记**禁止猜测**；⑤「宪法」九条含 **Simplicity / Anti-Abstraction / Integration-First**，并在 `plan` 阶段设 **Phase -1 Gates**；⑥ 模板强制**层级化细节**（主文档保持高层可读，细节外置到 `implementation-details/`） | **强适用**：⑤⑥ 可直接映射为「文档宪法 + 规模门禁 + 细节外置」；①③ 与本仓库已有的「README `mbt check` 文档测试」「门禁即契约」同源；④ 是本文 §7 状态字段的来源 |
| 2 | **Spec Kit 的收敛动作**（`implement → converge`，报告 `Converged`） | 实施后必须**回到规格做一致性收敛**，而非假设一次成功 | **强适用**：本仓库当前缺的正是「文档与实现的一致性收敛」——S11 的多次 v1→v2 复核就是手工版 converge，应机制化 |
| 3 | **Diátaxis**（文档四象限：Tutorial / How-to / Reference / Explanation） | 文档类型**不可混写**：一篇文档要么是「学习导向」要么是「任务导向」要么是「信息导向」要么是「理解导向」；混写是文档「感觉乱」的头号成因；四类各有自己的信息需求与校验方式 | **较强适用**：本仓库 `S*` 把「解释（为什么这么写）」与「参考（数字/表格）」写在同一篇（如 S9c 同时含结论表与实验设计），**符合典型混写症状**；但**不宜照搬四分类**（见 §2.2 边界） |
| 4 | 通用文档工程实践（README 作为落地页、计数不进正文、ADR/状态头、单文档规模上限、索引不复制目录） | **可发现性 > 完整性**：索引给「读者路径」，全量清单交给专门页；计数与版本号**必然漂移**，只留「结论 + 复跑命令」 | **已部分采纳**：`README优化-冗余清理与最佳实践` §6–§9 已把 README 压成落地页、计数清零；**未采纳到 `docs/` 内部** |

> **调研纪律**：以上为外部一手材料（Spec Kit 仓库原文、Diátaxis 站点）读后提炼，
> **不引用二手转述**；每条都给出「对本项目的适用性判定」，不做「照抄最佳实践」。
> 外部材料无版本锚点时（如 Spec Kit 快照），一律标注「2026 实读」，避免把它当成稳定契约。

### 2.2 本项目的边界：什么**不**适配（诚实声明）

1. **不引入 `specs/NNN-feature/` 目录与新编号体系**：本仓库的「spec 单元」是
   **模块级实现阶段（S1–S9）**，而非「按功能分支编号的需求」。引入第二套编号会与
   `S*` 系列、`scripts/`、`docs/移植参考/` 形成**三套坐标系**，净增认知成本。
2. **不做「规格生成代码」**：本仓库是**逐位对齐 Rust 参考库的移植**，
   真相来源是 `fast_qr` 钉版（`53e8c99`）+ 黄金值脚本，**不是**自然语言规格。
   强行让规格成为「生成源」会与「黄金值必须来自钉版」的 S10 铁律 1 **直接冲突**。
3. **不照搬 Diátaxis 四分类到每个文件**：本仓库已有事实标准——**S* 三段结构**
   （`实现方案` / `实现记录` / `评审与优化`）。四分类**作为「判别尺」**用于
   诊断混写（§5.2），但**不重命名文件为 tutorial/how-to/reference/explanation**。
4. **不追求「目录篇数最小」**：S11 §6.3 已判定 `docs/移植参考/**`（12 篇）**不建议合并**
   （分析对象是与主仓演化解耦的外部参考库）。本文继承该结论，**不纳入收敛对象**。

> 一句话：**取 SDD 的「闸门与信息架构」，不取它的「工作流重命名」**。

### 3.2 结构：标题层级与命名

实跑统计：

| 指标 | 实测 | 问题 |

### 5.2 Diátaxis 用作**判别尺**（不重构命名）

用四象限对现有篇章做**混写诊断**（抽样，逐篇可复核）：

| 篇章 | 主要类型 | 混写症状 | 建议 |
|------|---------|---------|------|
| `S1–S8`（实现规格） | Explanation + Reference | 三段式天然分离 ✅ | **保持为模板** |
| `S9c/S9e/S9f`（性能对比） | Reference + Explanation | 「结论表（参考）」与「为什么这么测（解释）」交错 | 结论表前移置顶，实验设计下沉（**不新开文件**） |
| `S9p/S9q`（口径与统计） | Explanation | 纯解释，结构清晰 ✅ | 保持 |
| `S10`（测试 roadmap） | How-to + Explanation | 铁律（规范）与覆盖矩阵（参考）同篇，776 行 | 已接近 800 行上限，**下次增量必拆** |
| `README优化-…`（9 轮总账） | Explanation（过程留痕） | 527 行、9 个平级 `## N.` 轮次 | **结构可读但已饱和**：新轮次应改为「索引行 + 承接篇」 |

> **Diátaxis 的正向价值**：它给出了「为什么读者觉得乱」的**可解释理由**——
> 不是内容多，而是**同一篇里同时要求读者「学」和「查」**。
> 本文据此把处置限定为**「结论前移 + 细节外置」**，而**不**改名、不拆文件。

### 5.3 「规格即契约」的映射（本项目已有，值得显式化）

本仓库实际已经实现了 SDD 最激进的一条——**可执行规格**：

- `README.md` 的 `` ```mbt check `` 块是**文档测试**，`moon test` 真编译真运行（改 API 不改示例即红）；
- 黄金值必须来自**钉版参考**（S10 铁律 1），`scripts/gen-goldens.sh --verify` 可校验未漂移；
- `diff-gate.sh` 与参考 wasm 逐位 sha256。

> **映射结论**：本仓库的「规格」是 **`.mbt` 源码 + `README.mbt.md` 文档测试 + `scripts/` 生成器**，
> **而 `docs/` 是它们的证据链与决策记录**。
> 因此 `docs/` 的准入条件应是「**能否指向一个可复跑的判定**」（§7.1 第 3 条），
> 而不是「是否写得详尽」。这条是本文与 S11「信息量」判据互补的第二把尺子。

## 6. 优化方案（D1–D7，按风险分级）

> **统一纪律**：一次一个主题、单独 PR；改完必跑 §1 ⑤ 的四项门禁；
> 移动文件必须同步 `docs/README.md` + `README.md` 索引（死链零容忍）。

### 6.1 P0：零文件移动、零信息损失（可直接做）

#### **D1 · 文档状态头 + 准入 CheckList**

给 `docs/**` 的 Markdown 增加**统一头部三字段**（Human 可读、机器可解析）：

```markdown
> 状态：现行 | 历史 | 已失效        ← 必填，取一
> 日期：YYYY-MM-DD（末次实质修订）   ← 必填（格式已有，仅统一）
> 索引：[docs/README.md](../../README.md) §N   ← 必填，指明在索引中的归属
```

- **`状态` 三值语义**（取代当前 18 篇自由措辞的 `⚠️ 历史记录`）：
  - `现行`：结论仍是对外口径，可直接引用；
  - `历史`：结论已并入某现行篇（**必须写 `并入：[篇名]`**），本文仅留过程价值；
  - `已失效`：所述前提已不存在（如 `wasm`(WASI) 后端移除、旧模块名），**不得被引用为口径**。
- **准入 CheckList（新增文档必过）**：
  1. 头部三字段齐备；
  2. 单文件 ≤800 行（AGENTS §四已定，此处纳入准入）；
  3. **每条结论能指向一个可复跑判定**（命令 / 门禁 / 生成器），否则降级为「讨论稿」不入 `docs/`；
  4. 若与既有篇结论重复 → **改既有篇**，不新开（反 R1）；
  5. 同步更新两处索引（`docs/README.md` + `README.md`）；
  6. `bash scripts/docs-link-check.sh` 零死链。

#### **D2 · 目录分类（只做「归类」，不做合并）**

把顶层 47 篇按**读者意图**归入 6 个子目录（**文件内容一字不改**，只换路径 + 全库改链接）：

```
docs/
├── README.md                      ← 新：目录首页（由现 README-导航与索引.md 改名/前移）
├── 01-规格/                        ← 读者：我要改代码
│   ├── S1..S9（实现规格与决策记录）
│   └── 工程约定（布局/目录/工具链）
├── 02-证据/                        ← 读者：我要审计数据
│   ├── S9*（性能/体积）
│   ├── S10*（测试）
│   └── S11*（清理审计）
├── 03-过程/                        ← 读者：我要复盘决策
│   ├── 历史基线（项目框架/roadmap/core 布局/wasm 编译）
│   └── 发布过程（mooncakes 发布/阻塞项/模块名迁移）
├── 04-元/                          ← 读者：我要改文档/README
│   ├── README 优化总账
│   ├── README 示例资产
│   └── S12（本文：文档体系规范）
└── 移植参考/                        ← 保持现状（外部语料，自成一域）
```

- **为什么用数字前缀**：`docs/` 在平台/编辑器中按字典序展示，数字前缀让**意图顺序**
  在文件列表里直接可见（`01-规格` 先于 `04-元`），且**不依赖平台渲染**。
- **为什么只归 6 类**：类目越多，新增文档越难归类（Spec Kit 的 Simplicity Gate）。
- **风险**：**这是唯一高改动量项**（47 篇路径 + 全库 ~600 条相对链接）——
  必须由 `docs-link-check.sh` 全量兜底，且**单独 PR、不夹带任何内容修改**（S11 §7-1）。

#### **D3 · 命名去序号化（别名优先，改名为辅）**

`S9n`、`S9r` 这类**内部代号**对读者零信息。两条路（可叠加）：

| 路线 | 做法 | 成本 |
|------|------|------|
| **A. 标题化（推荐先做）** | 文件名保留 `S9x` 以兼容既有 600 条引用，但**标题与索引表一律用语义名**（如 `S9n · 优化优先级与 wasm-gc 收敛审计`） | 低（只改标题/索引） |
| **B. 真改名** | 文件改为 `性能-优化优先级与收敛审计.md`，`S9n` 仅作尾部标记 | 高（须全库改链 + 更新 S 系列编号说明） |

> **建议**：本轮只做 **A**。理由：编号是本仓库**实现顺序的可追溯资产**（S1→S12 记录了移植史），
> 去掉编号会丢失「阶段可追溯性」这一 SDD 正向价值。**读者友好靠标题与索引，不靠文件名**。

### 6.2 P1：结构性收敛（需单独立项）

#### **D4 · 数字单点化 + 漂移门禁（本文最重要）**

1. **单点化**：每个易变计数/口径在 `docs/` 内**只允许一个「登记处」**——
   候选登记处：测试数 → `S10b`；性能三点 → `S9p`；体积 → `S9i`；版本号 → `README.md`（已定「不写死」）。
   其余篇章**一律写「见登记处」**，不复制数字。
2. **门禁化**：新增 `scripts/docs-consistency.sh`（秒级、离线）做三件事：
   - **① 状态字段**：`docs/**/*.md` 每篇头部须含 `> 状态：`，值域 `现行|历史|已失效`；
     `历史` 须带 `并入：`；`已失效` **不得**被其它现行篇当作现行口径引用；
   - **② 计数漂移**：从 `moon test` 实跑取 `Total tests: N`，与 `docs/` 内
     **标记为「登记处」** 的篇章值比对；不一致即红（其余篇章的非登记数字**不设为门禁**，避免噪音）；
   - **③ 索引覆盖**：`docs/**` 每篇必须在 `docs/README.md` 中出现（反 P4 漏更新）。
3. **接入**：加入 `scripts/gates.sh` 的 `DEFAULT_STAGES`（`docs-link-check` 之后）。
4. **必须带负向验证**（同 S11 §7 纪律）：注入一个错误计数 / 删掉一篇的状态字段 → 门禁须变红。

#### **D5 · 单文档规模与结构一致性**

- 维持 **≤800 行**（AGENTS §四已定，`test-scale.sh` 只管 `.mbt`，**文档侧无门禁**）→
  **把文档行数纳入 `docs-consistency.sh` ①**（≤800，超出须显式登记「已拆承接篇」）。
- **`S10`（776 行）** 距上限只剩 24 行 → 下次增量**必先拆**（建议按 S11b 模式拆出「落地记录」分册）。
- **`README优化-…`（527 行 / 9 个平级轮次）** → 后续轮次改为「轮次索引行 + 独立承接篇」，
  主篇冻结在「§0–§5 结论 + 轮次索引」。

#### **D6 · 「三段式」显式化为规范**

把 S1–S9 事实上的三段结构写成规范（§7.3），使新篇章**有模板可抄**：

```markdown
## 实现方案    ← 要做什么/为什么（含验收标准）
## 实现记录    ← 实际怎么做的（含与方案的偏离及原因）
## 评审与优化  ← 复核发现与结论去向
```

- **保留各篇已有的一字不改**（S11 §6.3 D7：阶段文档是移植可读性资产）；
  规范只约束**新增**篇章与**修订时**的增量段落。
- `S8/S9g/S9h` 等未走三段式的篇章**不强制回改**（回改成本 > 收益），
  仅在其头部 `状态：` 字段中登记结构差异。

## 7. 建议纳入 `AGENTS.md` 的规范条文（提案，待评审）

> 本节是**可直接粘贴进 `AGENTS.md` §四**的条文草案。本文**不代改 `AGENTS.md`**——
> 它属协作硬约定，应由维护者评审后单独提交（§9 队列 D2）。

### 7.1 文档准入（新增/修订文档前必过）

1. **头部三字段**：`状态`（现行/历史/已失效）、`日期`、`索引`（指明在导航中的归属）。缺一不予合入。
2. **单文件 ≤800 行**；超出须拆出「承接篇」并在两处索引登记。
3. **可复跑原则**：任何**数字结论**必须附复跑命令或指向登记处；无复跑路径的结论降级为「讨论稿」，不入 `docs/`。
4. **不新建「索引的索引」**：导航层次 ≤2 级（`docs/README.md` → 分类 → 篇章）。
5. **不合并已判定解耦的域**：`docs/移植参考/**` 不并入主域。
6. **索引双更新**：`docs/README.md`（全量）+ `README.md`（落地页入口）。

### 7.2 链接纪律（现状已闭环，条文化以免回退）

| 链接方位 | 形态 | 兜底门禁 |
|----------|------|---------|
| `README.md` → `docs/**` / `AGENTS.md`（**归档外**） | **仓库绝对链接** | `publish-check.sh` ⑤ |
| `docs/**` 内部互链（**仓库内导航面**） | **相对链接** | `docs-link-check.sh` |
| 图片资产 `docs/assets/**` | README 用 `/-/git/raw/main/...` 绝对直链 | `publish-check.sh` ⑤（含 HTML `src`） |
| 锚点 | `#fragment` 仅保留在相对链接或渲染面绝对链接 | 人工（渲染面才有效） |

### 7.3 篇章结构模板（新增文档抄这份）

```markdown
# S<N><x> · <语义标题>（不要只写代号）

> 状态：现行|历史|已失效　｜　日期：YYYY-MM-DD　｜　索引：<导航> §N
> 承接：[上位篇]　｜　并入：[若为历史，写明结论去哪了]
> 一句话结论：<本页唯一的 TL;DR>

## 实现方案 / 议题定义     ← 要做什么、为什么、验收标准（含「明确不做」）
## 实现记录 / 证据         ← 实际怎么做的、可复跑命令、与方案的偏离及原因
## 评审与优化 / 结论去向    ← 复核发现、结论去处、后续队列
```

### 7.4 一致性收敛（把「人巡检」换成「门禁」）

1. **数字**：只在登记处更新；`docs-consistency.sh` ② 与实跑比对。
2. **状态**：状态变更必须**同时**移动「引用它的现行篇」的表述，否则门禁 ① 红。
3. **索引**：新增篇章未入索引 → 门禁 ③ 红。
4. **新增门禁必须带负向验证**（注入错误 → 必须变红），与 S11 §7 纪律一致。
