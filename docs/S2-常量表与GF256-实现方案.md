> 承接 [S1-数据结构-实现记录](./S1-数据结构-实现记录.md) 的「下一步（S2+ 衔接）」与
> [moonbit-重写-roadmap-详细分析](./moonbit-重写-roadmap-详细分析.md) §4.2 的 **S2**：
> 落地 internal/constants（容量表 + 分组/格式信息/生成多项式硬编码表）与
> internal/reedsolomon（GF(256) 除法与分块交织），补齐 S1 因依赖容量表而推迟的
> `CompactQR::from_version` 与 `QRCodeError`，为 S3 encode 的容量判定铺路。

> 日期：2026-09-06　｜　前置：S1 已合入 main（PR #11）；本环境已补装 `moon` 0.1.20260827。
> 参考源码 fast_qr v0.14.0（commit `53e8c99`）：当前环境 `/tmp/fast_qr`、`/fast_qr` 均已不存在，

## 0. 一句话结论

S2 全部落在 **lib/internal/**（constants 两个叶包 + reedsolomon 一个包），**不触碰 lib 公共层**。
表数据一律由**提取脚本**从 fast_qr 参考源码生成并入库（禁止手抄，roadmap §3.2）；黄金单测抄
`tests/{version,polynomials,structure}.rs`。S2 完成后，S1 因无容量表推迟的三件事即具备落地条件：
`CompactQR::from_version`、`QRCodeError`（B8 骨架）与 `Version` 相关的矩阵元数据查表。

## 1. S2 范围界定（对照 roadmap §4.2）

来自 roadmap §4.2：

> **S2** | 常量表提取 + GF(256)（division/structure）| `hardcode.rs` / `version.rs:96` /
> `polynomials.rs:11-106` | `tests/version.rs`、`tests/polynomials.rs`、`tests/structure.rs`

对应 roadmap §4.3 迁移批次 **B2 / B3 / B4**，与 §4.4 里程碑 **M0** 的常量/GF 一侧。

| 批次 | 源文件 → 目标 .mbt | 关键交付 | 黄金来源 |
|:---:|-------------------|---------|----------|
| B2 | `version.rs` → `internal/constants/capacity.mbt` | 容量/矩阵元数据表 + `get`/`max_bytes`/`information`/`alignment_patterns_grid` 查表 | `tests/version.rs`（3876 行）|
| B3 | `hardcode.rs` → `internal/constants/hardcode.mbt` | `ecc_to_groups`（u32 位打包）/格式信息/`get_polynomial` | 表值抽测 + `tests/hardcode` 对应项 |
| B4 | `polynomials.rs` → `internal/reedsolomon/reedsolomon.mbt` | LOG/ANTILOG + `division` + `structure` | `tests/polynomials.rs`（1168 行）+ `tests/structure.rs`（489 行）|

**不属于 S2**：
- encode 三模式与容量自动选择 → S3（B7）——但 S2 提供的 capacity 查表正是 S3 容量判定的数据底座
- 功能图案/放置/掩码 → S4/S5（B9/B10）
- 输出层 → S7
- `QRCodeError`/`QRBuilder` 组装 → S3/B8（S2 只把「判容量的表」备好，抛错入口归 encode/B8）

## 2. 前置条件与准备

### 2.1 恢复 fast_qr 参考源码（S2 的硬前置）
S1 记录称参考源码克隆于 `/tmp/fast_qr`（master `53e8c99`），**当前环境该目录已不存在**。
S2 的表与黄金测试都依赖它，故第一步重新检出并**固定到与 roadmap 一致的 commit**：

```bash
git clone https://github.com/erwanvivien/fast_qr <tools_dir>/fast_qr   # 不入库（放 /tmp 或 tools/，见 .gitignore）
cd <tools_dir>/fast_qr && git checkout 53e8c99   # 锁定 v0.14.0，保证表/黄金与文档一致
```

> 产出表数据与黄金断言的脚本放在 `tools/`（不入库，或直接临时脚本），结果（生成的
> capacity.mbt / hardcode.mbt 表 + 黄金 `_test.mbt`）入库。遵守 AGENTS §二「禁止手抄、表由脚本生成」。

### 2.2 读表脚本要点（从参考源码生成）
参考 `version.rs` / `hardcode.rs` / `polynomials.rs` 全为编译期常量（`const fn`/`const`），
但**不要求在 MoonBit 运行时复算**——用**提取脚本**在 Rust 语义下把这些常量表**展开成
MoonBit 的数组/查表函数字面量**写入 `capacity.mbt`/`hardcode.mbt`。脚本应同时输出：
1. 各常量表（容量矩阵、分组表、LOG/ANTILOG 等）的 MoonBit 数组字面量；
2. 由 `tests/*.rs` 期望值转译的黄金断言常量。

> 关键：MoonBit 不支持 Rust `const fn` 嵌套 match 的表生成；S2 选择「表展开为常量数组 +
> 运行时纯查表」既对齐性能决策（roadmap §2.2 第 4 条：编译期常量表 + 运行时查表），
> 又绕开语言差异。数组量级：`[u8; 255]` LOG/ANTILOG、`[u8; 5430]` structure 上限、
> 40×4×3 容量表等均在 MoonBit 固定/动态容器可承载范围内。

## 3. 各交付物设计要点

### 3.1 `internal/constants/capacity.mbt`（B2，叶节点）
对应 `version.rs` 中与「版本选择/容量/矩阵元数据」相关的部分：

| 交付 | 语义 | 参考锚点 |
|------|------|---------|
| 容量查询 `capacity(version, mode, ecl) -> Int` | 按 (序号, 模式序号, ECL 序号) 返回容量（比特/字节）| `version.rs:96` const fn `get` |
| `max_bytes(version, ecl) -> Int` | 该 (版本, ECL) 总数据字节上限（S1 推迟的 `from_version` 依赖它）| `version.rs` |
| 矩阵元数据 `information` / `alignment_patterns_grid` | 版本信息字、对齐图案网格坐标（供 S4 图案层）| `version.rs` 同名方法 |
| `size(version)` / `missing_bits` 等 | 边长与容量相关辅助 | `version.rs` |

> 依赖规则：**叶节点无依赖**，只提供以 `Int` 序号入参的查表函数，不 import lib（公共枚举
> 以序号传入，layout 文档 §4 边界约束）。S3 encode 会消费 capacity；S4 消费 alignment 网格。

### 3.2 `internal/constants/hardcode.mbt`（B3，叶节点）
对应 `hardcode.rs`（B3）：

| 交付 | 语义 | 参考锚点 |
|------|------|---------|
| `ecc_to_groups(version, ecl) -> ...` | 分组信息；Rust 用 `(count<<24)|(size<<16)|...` 打进 u32，解码取回 | `hardcode.rs:14` |
| 格式信息表 / 版本信息 | 掩码择优后写真实 Format（S4/S5 用）| `hardcode.rs` |
| `get_polynomial(ec_index) -> ...` | 生成多项式（长度即纠错码字数，≤30）供 division 查表 | `hardcode.rs:324` |

> 依赖规则：叶节点，供 reedsolomon / matrix 查表。

### 3.3 `internal/reedsolomon/reedsolomon.mbt`（B4，→ constants）
对应 `polynomials.rs`（B4），是本阶段唯一带算法的一环：

| 交付 | 语义 | 参考锚点 |
|------|------|---------|
| `LOG` / `ANTILOG`（[u8;255] 常量）| GF(256) 幂/对数查表 | `polynomials.rs:11-42` |
| `division(data, generator) -> [u8;255]` | 域除法取余（纠错码字）；查表 + 异或 | `polynomials.rs:83` |
| `structure(data, ecl, version) -> [u8;5430]` | 分块纠错 + 数据/纠错码字交织 | `polynomials.rs:106` |

**关键语义（照抄，framework §五.8 / gf256 概念文档）**：
- 除法：数据右对齐放 `[0;255]`，对每个非零首项 `alpha=ANTILOG[首项]`，逐生成项 `^= LOG[(by[j]+alpha)%255]`；余数即尾部 `generator.len()-1` 字节。
- 交织：数据区**逐块跨字节**、纠错区**逐字节跨块**（方向相反）；纠错区索引
  `start_error_idx + j*groups_total + i`。
- 上限常量：`MAX_ERROR=30`、`MAX_GROUP_COUNT=81`、`MAX_DATABITS=3000`、`structure` 固定 5430。
- 表驱动：所有域运算查表，禁止运行时算 alpha 幂。
- `% 255` 加法无负数场景，仍建议加越界断言（roadmap §3.2）。

> 依赖规则：仅 → `internal/constants`（取分组/生成多项式），不 import lib；ecl/version 以序号入参。

## 4. 与 S1 的衔接（S2 完成即解锁的事项）

| S1 推迟项 | 解锁方式 | 落点 |
|-----------|---------|------|
| `CompactQR::from_version(v)` | `capacity.mbt` 提供 `max_bytes(v, ecl)` 后，`from_version(v)` = `from_bits(v.max_bytes()*8)`；在 `lib/internal/bitstream` 内补 fn + 黄金测试 | B6 补丁 |
| `QRCodeError`（`EncodedData`/`SpecifiedVersion`）| 容量判定路径就绪（S3 encode 用）后在 lib 公共层定义并构造 | B8 骨架 |
| Version 矩阵元数据查表 | `alignment_patterns_grid`/`information` 等就绪，供 S4/S5 用 | B2 |

> 注：`QRCodeError` 仍会受 MoonBit `--deny-warn` 的 `unused_constructor` 约束——必须等到
> S3/B8 存在可达构造路径才能落枚举，S2 阶段可先把 `from_version` 补上、并在 capacity.mbt
> 内部以「查表越界回退」或测试驱动方式让它被用到，避免半成品门禁。

## 5. 测试与验收

- 表值抽测 + 黄金转译：
  - `capacity.mbt` 黄金抄 `tests/version.rs`（3876 行，量大——脚本转译）
  - `reedsolomon` 黄金抄 `tests/polynomials.rs`（1168 行）+ `tests/structure.rs`（489 行）
  - `hardcode` 分组/多项式表抽测 + 交叉验证
- 回归门禁（沿用 AGENTS §二.4）：
  ```bash
  moon fmt && moon info && moon check --deny-warn && moon test
  for t in wasm-gc wasm js; do moon build lib --target $t --release; moon build cmd/main --target $t --release; moon test --target $t; done
  ```
- `.mbti` 护栏：lib 公共面**不得**出现 internal/constants、internal/reedsolomon 类型
  （用 `moon info` 核对；这些包的函数若 `pub`，会进各自 `.mbti`，但只要 lib 不引用即不出现在 lib 契约）。

> 验收即完成里程碑 M0 的常量/GF 一侧，为 S3 encode + S4 放置提供数据与纠错底座。

## 6. 实现顺序与提交切分

参考 roadmap §4.3 提交切分，每批一个提交、消息 `feat(qr): 迁移 <模块>（参照 <Rust 文件>）`：

1. 恢复 fast_qr 克隆并写提取脚本 → 生成 `capacity.mbt`（表）+ 黄金 `_test.mbt`（提交表与测试）
2. `hardcode.mbt`（B3）
3. `reedsolomon.mbt`（B4）division → structure，逐层绿
4. 回填 `bitstream` 的 `from_version` + 测试（B6 补丁）
5. 收尾：`README`/roadmap 实现状态更新（把 S2 记为「已规划/进行中」）

> 边界检查：internal 各包 `moon.pkg` 只在用到时声明 import 且声明即使用，避免 `unused_package`
> （layout §1.5）；`--deny-warn` 下未用常量用测试驱动覆盖。

## 7. 风险与评估

| 风险/难点 | 评估与对策 |
|-----------|-----------|
| 参考源码已丢失于环境 | S2 第一步克隆并**锁 commit**，全流程以 `53e8c99` 为准（§2.1）|
| 大表生成手抄易错 | 一律脚本生成 + 黄金对照；禁止人工抄写（AGENTS §二）|
| `unused_constructor`/`unused_const` 门禁 | 表在 S2 通过测试被引用，或延迟到 S3 再全面 use；避免半成品 |
| division/structure 交织方向 | 严格照 framework §五.8 与 concept 文档；用 structure.rs 黄金逐位核对 |
| MoonBit 缺 Rust `const fn` | 用「脚本展开为常量数组 + 运行时查表」等价对齐性能决策 |
| reedsolomon 依赖 constants | 依赖方向 constants（叶）→ reedsolomon 单向，无环 |

> 一句话评估：S2 风险集中在**表数据正确性**（用脚本+黄金对冲）与 **division/structure 交织细节**
> （用 concept 不变量+黄金对冲），难度低于 S5（掩码择优），**可在 S1 基础上直接推进**。
