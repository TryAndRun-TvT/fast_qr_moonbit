## 0. 一句话结论

mooncakes 账户确定为 **`TryAndRun-TvT`**（与 CNB 组织名 `tryandrun` **不同名**），
故模块名由 `tryandrun/fast_qr_moonbit` 迁移为 **`TryAndRun-TvT/fast_qr_moonbit`**；
改名后 `moon check` / `moon test` / `scripts/publish-check.sh` 全绿，
`moon publish --dry-run` 实测服务端 `202 Accepted`（**退出码 255 是该版本 CLI 的已知行为，非失败**，见 §3）。

## 1. 报错现象与根因

### 1.1 现象

只改 `moon.mod` 的 `name`、未同步 `moon.pkg` 时，`moon publish`（其内部先跑 `moon check`）直接失败：

```text
Running moon check ...
Error: Failed to calculate build plan

Caused by:
    0: Failed to solve package relationship
    1: Cannot find import 'tryandrun/fast_qr_moonbit/lib' in TryAndRun-TvT/fast_qr_moonbit/cmd/bench@0.1.0

moon check failed
Error: `moon publish` failed
```

### 1.2 根因

- MoonBit 的**包全名 = `<模块名>/<包相对路径>`**，模块名由 `moon.mod` 的 `name` 唯一决定。
- `moon.mod` 改名后，包 `cmd/bench` 的全名变成 `TryAndRun-TvT/fast_qr_moonbit/cmd/bench`，
  但它 `import` 的仍是旧全名 `tryandrun/fast_qr_moonbit/lib`；
  构建系统在**解包依赖关系（build plan）阶段**就找不到该包 → 与 `.mbt` 代码无关，
  因此**改代码/清理 `_build/` 都无效**，必须改 import 路径。
- 报错只点名 `cmd/bench` 是**首个被解到的失败点**，并非只有它有漏改：
  凡声明了旧前缀的 `moon.pkg` 都会中招（本次共 9 个）。

### 1.3 迁移规则

| 位置 | 旧值 | 新值 |
|------|------|------|
| `moon.mod` 的 `name` | `tryandrun/fast_qr_moonbit` | `TryAndRun-TvT/fast_qr_moonbit` |
| `moon.pkg` 的 `import` 前缀 | `tryandrun/fast_qr_moonbit/...` | `TryAndRun-TvT/fast_qr_moonbit/...` |
| 归档产物名 | `tryandrun-fast_qr_moonbit-0.1.0.zip` | `TryAndRun-TvT-fast_qr_moonbit-0.1.0.zip` |
| 文档/CI/脚本示例 | 同上 | 同上 |

> **不改名的地方**：CNB 组织名与仓库地址（`https://cnb.cool/tryandrun/moonbit_dev/fast_qr_moonbit`）、
> `tryandrun/rust_dev/rs-site-tools` 等**外部仓库引用**保持原样——它们与 mooncakes 账户名无关。
> 即：「CNB 组织 `tryandrun`」≠「mooncakes 账户 `TryAndRun-TvT`」。

## 3. 已知 CLI 行为：`moon publish --dry-run` 恒返回 exit 255

```text
Server status: 202 Accepted, detail: Dry run completed successfully. No changes were made.
Error: `moon publish` failed        ← 进程退出码 255
```

- **与仓库内容无关**：用全新空模块复现（`moon new` 后立即 `moon publish --dry-run`）
  得到**完全相同**的 `202 Accepted + exit 255`。
- **判据**：干跑是否通过只看服务端回执 `202 Accepted ... Dry run completed successfully`，
  **不要**只看退出码，否则会把「干跑成功」误判成发布失败。
- 影响面：`scripts/` 与 CI 若要用退出码卡干跑，需改为**匹配输出文本**。
- 未验证项：真实 `moon publish`（非 dry-run）的退出码，**待维护者执行 C3 时回填**。

## 4. 核验方式（最小复现）

```bash
export PATH="$HOME/.moon/bin:$PATH"

# ① 依赖/build plan：改名是否彻底（本次报错的直接复验）
moon check --deny-warn                 # -> Finished. moon: ran 26 tasks, now up to date
grep -rn "tryandrun/fast_qr_moonbit" --include=moon.pkg --include=moon.mod .   # -> 无输出

# ② 质量基线
moon fmt --check
moon test                              # -> Total tests: N, passed: N, failed: 0（计数见 S10b 登记处）

# ③ 发布前门禁（归档面 32 项 + 内容白/黑名单 + 元数据 + 质量基线）
bash scripts/publish-check.sh          # -> 全绿；④ name 形如 <user>/<module>：TryAndRun-TvT/fast_qr_moonbit

# ④ 发布链路干跑（需本地 moon login）
bash scripts/publish.sh                # ①~④ 全含：自检 + 门禁 + 归档清单 + dry-run
                                       # -> ✅ 干跑通过（Server status: 202 Accepted；exit 255 见 §3）
bash scripts/publish.sh --publish      # 真实发布（不可逆，需确认；见 §6）

# 附：等价于原 push 流水线的一键全量门禁
bash scripts/gates.sh
```

## 5. 同期变更：`.cnb.yml` push 流水线移除（2026-09-14）

- 原 `push` 流水线（setup-moonbit / fmt-check / check / test / docs-link-check / test-scale /
  build-and-run / diff-gate / publish-check）**整体移除**，原因是每次推送重复全量构建+测试，
  资源占用与当前迭代收益不成比例。
- **门禁未削弱**：各阶段命令本就抽离在 `scripts/` 下（零改动），改为本地/发布前按需执行：
  `bash scripts/gates.sh`（等价于原 push 流水线的全量链，支持 `STAGES=` / `SKIP_SLOW=1`）。
- 发布动作同样脚本化：`bash scripts/publish.sh`（默认干跑，`--publish` 才真发，见 §4）。
- 副作用：质量闸门由「推送触发」变为「人触发」，故提交前本地跑一遍是**必须**动作
  （`AGENTS.md` §二.4 已加注记）。
