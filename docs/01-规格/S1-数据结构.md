### 3. 各交付物设计要点

#### 3.1 `ECL`（lib/ecl.mbt，B1）

- 4 个变体 `L / M / Q / H`，**Q 为默认**（参考接口文档 §1.3，fast_qr 默认 ECL=Q）。
- 需要 `序号映射`：S1 先落一个返回 `Int` 序号（供后续 capacity 表第一维查表用）的访问器。
- MoonBit 若支持给枚举显式值，用 `0..=3`；否则枚举 + `fn to_int(self) -> Int`。

#### 3.2 `Version`（lib/version.mbt，B2 骨架）

- 40 变体 `V01..V40`，序号 `0..=39`（Rust 判别值 0-39）。
- 提供 `to_int()` / 序号范围断言。**容量大表放 S2 internal/constants/capacity.mbt**，
  S1 不实现查表，避免提前引入 unused import。

#### 3.3 `Mode` / `Mask`（骨架）

- `Mode`: `Numeric / Alphanumeric / Byte`。
- `Mask`: 0-7（`Checkerboard / HorizontalLines / VerticalLines / DiagonalLines /
  LargeCheckerboard / Fields / Diamonds / Meadow`）。
- S1 仅建枚举骨架（供 lib API 面定型），映射逻辑随对应批次（B7/B10）补齐。

#### 3.4 `QRCode` 与错误（lib/qr.mbt，B8 骨架）

Rust `QRCode`（qr.rs:25）字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `data` | `[Module; 31329]` | 一维固定数组，按行存储；实际有效 `size*size` |
| `size` | `usize` | `version*4 + 17` |
| `version/ecl/mask/mode` | `Option<...>` | 实际使用值（`Option` 因支持自动选择） |

- **固定容量矩阵**：177×177=31329 模块。MoonBit 用**固定大小容器**（一次分配、零扩容）。
- 错误收敛为两类（对齐 Rust `QRCodeError`）：
  - `EncodedData`：数据超出容量
  - `SpecifiedVersion`：指定版本过小
- S1 落：容器 struct 定义 + 元数据字段 + 错误类型 + 基础构造（仅结构，不含 encode 管线）。

#### 3.5 `CompactQR` → `bitbuffer`（B6，internal/bitstream）

来自 [compact-qr.md](../移植参考/专有概念/compact-qr.md)：

| 项 | 语义 |
|----|------|
| `len` | 已写入比特数 |
| `data` | 大端序位流字节容器（高位在前），预分配 |
| `from_version` | 容量 = 版本最大字节数 × 8 比特 |
| `push_bits(bits, len)` | 超出位被 `KEEP_LAST[len]` 截断 |
| `push_u8` | 逐字节写入 |
| `fill()` | 交替写 `0b1110_1100 / 0b0001_0001`（236/17）|

- **平台位宽风险**（roadmap §3.2 / 框架文档 §五.3）：`KEEP_LAST` 在 wasm32=33 项、64 位=65 项。
  MoonBit `wasm`/`wasm-gc`/`js` 后端实现时必须核对截断位数，用显式掩码避免 `usize` 位宽漂移。
- **黄金数据**：抄 `/fast_qr/src/tests/compact.rs`（200 行）期望值转译为白盒断言。

### 4. 关键架构决策（S1 必须先拍板）

> 这是 S1 的核心难点，来自「Module 需进 public 契约（Rust crate 根导出）」与「internal 永不反向
> 依赖 lib / internal 类型不进 `.mbti`」两条布局约束的张力。决策影响 `QRCode.data` 的类型与
> `module.mbt` 的落点，**必须在第一个提交前定案**。

#### 现状张力

- Rust：`Module` 是 crate **公共**导出，`QRCode.data: [Module; 31329]`，用户逐行读取拿 Module。
- MoonBit 布局文档 §3.2 / §4：`module.mbt → internal/matrix`，且 **internal 不反向 import lib**、
  **公共枚举只在 lib**、internal 类型不应对 lib 公共接口可见（否则泄漏进 `.mbti`）。
- 若 `QRCode.data` 直接引用 `internal/matrix.Module` → internal 类型泄漏到公共 `.mbti`，违反封装。

#### 决策建议（推荐 **D1**，备选 D2）

**D1 — Module 上移为 lib 公共层类型（薄包装），internal/matrix 用「字节」独立实现位操作**
- 在 lib 公共层定义 `Module`（单字节：bit0 明暗 + bit1-3 类型）作为**对外契约/呈现类型**，
  对齐 Rust crate 根导出；`QRCode.data` 用它，用户可读明暗/类型。
- internal/matrix 的放置/掩码/评分**不依赖 lib**，直接对原始 `u8` 字节数组做位运算
  （掩码只 toggle Data、`module_type()` 判类型等用 u8 掩码即可），返回字节结果给 lib；
  lib 侧把字节包装为公共 `Module` 呈现。
- 依赖方向保持：lib → internal/matrix（取字节结果）；internal 不依赖 lib ✓。
- 代价：Module 位语义在 internal（u8 直算）与 lib（薄包装）有轻微重复，用**同一份位布局文档**
  （§3.1 module 位规则）锁死，并用两端白盒测试防漂移。

**D2 — Module 保持在 internal/matrix，QRCode 不直接暴露 Module**
- `QRCode.data` 内部存字节（或私有数组），对外给 `dark_at(row,col): Bool` / `module_type_at(...)` 等
  访问器，不暴露 internal 类型。
- 优点：封装最干净、`QRCode` 不依赖 internal 的类型名。
- 缺点：与 Rust 公共 API 的 `Module` 契约不一致，能力对齐（框架文档 §2.4）略打折；且 S7 渲染/
  S9 输出层仍需逐模块信息，访问器方式可行但 API 面较 Rust 扁平。

> **落地判据**：若追求「与 fast_qr 公共 API 能力对齐」（框架文档 §2.4、验收定义②），推荐 **D1**；
> 若更重视 internal 强封装、公共面最小化，选 **D2**。S1 应选定其一并在 `lib/qr.mbt`、`module.mbt`
> 落地前用 `moon info` 检查 `.mbti`，确认公共面不含 internal 类型。

### 2. 实测解决的「待实测决策」（S1 方案 §5）

#### 2.1 固定大小矩阵 → 用 `Array[Module]` 预分配（方案 §5.1）
MoonBit 固定容量容器 `[Module; 31329]` 在类型面不易表达，实测采用
`QRCode.data : Array[Module]`，经 `Array::make(QR_MAX_MODULES, light)` 一次性预分配
到 31329（`QR_MAX_MODULES=31329`；最大边长 177 由 `Version::V40.width()` 表达，S11 v4 删冗余常量 `QR_MAX_WIDTH`）。语义对齐 Rust「固定容量、按行
存储」：所有 QRCode 恒为 31329 槽，有效区 `size*size`，越界槽不参与渲染。
（正是方案 §5.1 给出的 Array 兜底；若后续测量到必要可再评估固定容器。）

#### 2.2 枚举原始判别值（方案 §5.2）→ 用「枚举 + 序号映射」方案
MoonBit 枚举不支持 Rust 式显式判别值；采用方案 §5.2 的备选：枚举变体顺序 + `to_int()`
序号映射函数，`from_int()` 供回读。序号与 Rust 判别值一致：
`ECL` L/M/Q/H=0..3、`Version` V01-V40=0..39、`Mode` 0..2、`Mask` 0..7。

#### 2.3 Module 归属 → 采纳 **D1**（方案 §4）
`Module`/`ModuleType` 上移 `lib/module.mbt` 作公共呈现类型，与 Rust crate 根导出对齐；
`QRCode.data` 用公共 `Module`。内部掩码/放置等字节位运算待 S4+ 在 `internal/matrix`
独立实现（不反向依赖 lib）。**`moon info` 实测：lib 公共面不含 internal 类型**（§5 验收项）。

#### 2.4 KEEP_LAST 位宽 → 32 位 Int（方案 §5.4 / roadmap §3.2）
MoonBit `Int` 为 **32 位**，故 `keep_last` 取 Rust **wasm32 分支**规模：
`keep_last[k] = (1<<k)-1`（k=0..=31，32 项）。QR 编码单次 `push_bits` 位数上界 ≪ 32
（模式 4 + 计数 ≤16 + 段 ≤10/11），安全；三后端 `wasm-gc`/`wasm`/`js` 均 32 位 Int，行为一致。

#### 2.5 依赖声明 → 只在用到时声明
S1 `lib/moon.pkg` 仍为空（公共类型自成一体，无需 import internal）；`internal/bitstream`
的测试由 `moon test` 模块级发现并运行（实测确认），无 `unused_package` 告警。

### 3. 实现中拍板/偏离方案的新决策

#### 3.1 公共可构造枚举需 `pub(all)`（重要发现）
MoonBit 中，`pub enum` 的**变体**在**包外不可构造**（报 `Cannot create values of the
read-only type`），只有函数可 `pub` 跨包调用。因此凡是需让调用者直接构造的公共枚举/
结构（`ECL`/`Version`/`Mode`/`Mask`/`ModuleType`/`Module`/`QRCode`）一律声明为
**`pub(all)`**；仅内部 helper 函数用 `pub`。实测：`pub(all)` 后黑盒测试与真实消费方
均可 `ECL::Q`、`Version::V01` 等构造。

#### 3.2 `QRCodeError` 推迟到 S3/B8（偏离方案 §1 属于 S1 的条目）
MoonBit `--deny-warn` 的 `unused_constructor` 要求每个枚举变体都在**可达非测试代码**中
被构造。S1 尚无产生 `EncodedData`/`SpecifiedVersion` 的路径（需 encode 容量判定，属
S3/B8），故**推迟 `QRCodeError` 枚举定义**到 B8 与容量判定一并落地。`QRCode` 容器及
错误收敛面的设计（两类错误）已在方案文档与 `qr.mbt` 注释中固化。

#### 3.3 `from_version` 推迟到 S2（CompactQR 用 `from_bits(capacity_bits)`）
`from_version` 依赖 `version.max_bytes()`（版本容量表，属 S2）。S1 以
`from_bits(capacity_bits)` 作为原始容量构造入口，编码期零扩容、按需 `push`；
S2 容量表就绪后，再补 `from_version(v)` = `from_bits(v.max_bytes()*8)`。

#### 3.4 不可变式写入风格
MoonBit 值类型缺 `&mut self`，本项目结构以**不可变式**为主（如 `Module::set/toggle`、
`QRCode::set` 返回新值）。`CompactQR` 位流因写入密集采用 `mut len` 字段 + 就地改 `Array`，
对应 Rust `&mut self` 语义。

### 3. 发现的问题与优化

#### 3.1 【已修复·真实 BUG】`QRCode::set` 别名写穿，破坏「不可变式」语义
- **现象**：`QRCode::set` 内部 `let data = self.data` 后 `data[row*size+col]=m` 再以同一
  `data` 构造新 `QRCode` 返回。MoonBit `Array` 是**引用类型**，故返回的新 QRCode 与源 `self`
  **共享同一底层数组**——调用 `qr2 = qr.set(...)` 会**顺带把 `qr` 也改了**。
- **与声明冲突**：实现记录 §3.4 声称「`QRCode::set` 返回新值」不可变式写入，实为别名写穿。
- **验证**：新增回归测试
  `qr_code_set_immutable_no_alias`（先 `qr.set` 取 `qr2`，再断言源 `qr.get(0,0)` 仍为亮）——
  修复前**失败**（`true != false`），修复后通过。
- **修复**：写入前先 `let data = self.data.copy()`，真正隔离源数组。见本批 PR。
- **影响面**：现无 encode 调用方，故纯 API 正确性问题；S4/S5 若误用共享写会造成难查的耦合
  bug，必须现在修。`.mbti` 公共面未变（内部行为修复，安全重构）。

#### 3.2 【已评估·无需改】`QRCode::get/set` 无越界检查
`get(row,col)=data[row*size+col]` 不做范围断言。S1 为骨架、调用方受控（内部/测试），
符合 fast_qr 固定容器契约。**建议**：S4 真正写矩阵时，若担心调试可在 debug 下加断言，
但非 S1 阻塞项。

#### 3.3 【已评估·记录】D1 带来的 Module 位语义两处重复（lib / internal）
D1 让 lib `Module`（公共呈现）与未来 `internal/matrix/module.mbt`（算法层字节直算）各自维护
「bit0 明暗 + bit1-3 类型」位布局，**存在漂移风险**。S1 方案已用「同一份位布局文档 + 两端白盒
测试」对冲。**优化建议**：S4 落地 internal/matrix 时，其字节布局务必**复用本 doc 锁定的位规则**
（`序号<<1`），并用与 lib 相同的 Module 白盒断言（抄 module.rs 语义）防漂移——已在 S4 规划中标注。

#### 3.4 【已评估·无阻塞】`push_bits` 尾段用 `+` 而其余用 `|`
bitbuffer `push_bits` 收尾部分写残余字节用 `+`（其余段用 `|`）。实测黄金 11 例三后端全绿，
与参考语义一致（该字节为当次新写、无既有位重叠，`+` 不产生进位越位）；但为风格统一与防
未来回归，**建议后续 B6 补丁统一为 `|`**，属可选项（非 bug，因语义等价）。

#### 3.5 【已评估·维持】性能观察
- `QRCode::set` 修复后每次 O(size²) 拷贝（31329）。S1 仅容器构造/测试用，量级可接受；
  真正热写发生在 S4 internal/matrix 的原始字节数组上（就地 `mut`），lib 侧仅收尾包装一次。
- bitbuffer 用 `mut len` + 就地改 `Array` 对应 `&mut self`，写入密集路径已按不可变外层/可变内层
  分层，无需改。
