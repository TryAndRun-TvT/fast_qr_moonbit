## 0. 一句话结论

S9 = 把参考库 fast_qr v0.14.0 的 **criterion 三基准点 V03H/V10H/V40H**（输入固定 `https://example.com/`，
criterion 200 样本 × 10s）在本仓库移植出可复跑的**基准**并产出**透明对比数字**，收敛 M3「三基准点可跑并给出
对比数字；后端/产物分发结论记录在案」。关键评估结论（**按「本项目与 fast_qr 主比较 **wasm 产物性能**」的
定位，修订对比分层，把「对 fast_qr 的 wasm 对比」从 deferred 提到当前环境可落地层**）：

1. **参考数字是 Rust `native` 的 82.2/269.3/2436.2 us（64 位 native）**；而本环境 **`native` 后端不可用**
   （无 C 编译器，AGENTS §二.3）。更关键的架构事实（§2.1）：本仓库 MoonBit `Int` 为 **32 位**，
   `bitstream/bitbuffer.mbt` 的 `KEEP_LAST` 取的是 Rust **wasm32 分支**（index 0..=31、33 项），且**对全部
   后端生效**（不只 wasm）——这份 MoonBit 移植在内存位宽语义上本身就是 **wasm 形态**，与其语义最贴近的
   fast_qr 参照物是 **wasm32 build（KEEP_LAST=33）**，而非 64 位 native（KEEP_LAST=65）。因此 S9 的「对比」
   **三层分层**：
   - **层① 跨后端选型（同源码）**：wasm-gc / wasm 双后端跑三基准点，横向比体积/耗时（同源码语义互证），
     复刻并升级 docs/wasm §5.2 到「真实 QR 生成路径」；
   - **层② 对 fast_qr 的 wasm 对比（同执行模型，当前环境可落地，本仓库真正主口径）**：检出 fast_qr
     跑 `wasm-pack.sh` 产物（`fast_qr_bg.wasm`，wasm32），MoonBit wasm-gc/wasm 对 fast_qr-wasm32 逐位
     对齐 + 同一宿主计时；**不依赖 C 工具链**，与「wasm 产物 + 对 fast_qr」的选型叙事同源；
   - **层③ native MoonBit vs fast_qr native（可选方法学注记）**：留具 C 工具链环境执行，仅量级参考，
     注明内存模型差异，**不是主口径**（拿 wasm 形态的 MoonBit 对 64 位 fast_qr 反而更不同源）。
2. **载体**：MoonBit 无内置 criterion；本仓库现状无任何 bench 机制（`_bench_test.mbt` 仅 core 参考文档
   提及、顶层 `bench/` 基座为 P2 待办）。S9 最小可行 = 一个**可复跑的独立基准包/命令**（如 `cmd/bench`）+
   宿主计时脚本；不空建顶层 `bench/`。`cmd/bench` + `scripts/bench.sh` 的宿主计时口径**可同时喂给层①与
   层②**（检出 fast_qr 跑 wasm-pack 产物、同一宿主计时脚本），不必等 native。
3. **优化做不做**：S9 定位是「测出当前数字 + 透明对比」，**不是**大改性能。S5/S6 已列多条非阻断优化
   （§2.2）留 S9——S9 只承接其中**零风险/独立**的微优化并在基准前后各测一次做佐证；涉及正确性敏感的主
   循环重构（如 8 轮 clone→就地翻转）**不并入 S9**，单列 P2 待后续专项，避免破坏快照对齐。
4. **版本语义待实现时核对**：三基准点同输入、只差版本，需强制 `.version(V03/V10/V40)` × `.ecl(H)`；
   V03H 恰为 19 字节 Byte-H 的最小适配版本（V03 Byte-H 容量 24 ≥ 19），V10/V40 为强制升版（§3.1 论证）。
   fast_qr 侧 wasm32 的 `benches`/`wasm.rs` 是否走自动择优需对参考核对（§3.1）；因 fast_qr wasm 侧
   KEEP_LAST 已截断为 33，跨版本结果应与 64 位 native 一致（同一算法），正适合做「MoonBit wasm ↔ fast_qr
   wasm」**逐位对齐 + 计时双验证**。

## 2. 现状盘点（动手前已读代码 + 文档）

### 2.1 可用产物与后端事实（实测/文档）
- 模块 `supported_targets = "+wasm+wasm-gc"`，`preferred_target = "wasm-gc"`；**无 native**（需 C 编译器，
  当前镜像未装，AGENTS §二.3）。兼容产物 `--target wasm`（WASI preview1）。
- **内存位宽事实（架构层关键）**：MoonBit `Int` 为 32 位，`lib/internal/bitstream/bitbuffer.mbt` 的
  `KEEP_LAST` 取 Rust **wasm32 分支**规模（index 0..=31、33 项，见文件头注释与 `keep_last` 字面量表），
  且这份表是**模块内唯一定义、对全部后端生效**（不只 wasm）。故本仓库整体在内存位宽语义上是 **wasm
  形态**（KEEP_LAST=33），最贴近的 fast_qr 参照物是 **wasm32 build**（KEEP_LAST=33），而非 64 位 native
  （KEEP_LAST=65）。
- 公共入口就绪：`QRCode::build`（自动/固定 mask）、`QRCode::build_fixed`、`QRBuilder`（new/from_string +
  mode/ecl/version/mask 链式 + build），可强制 ecl/version/mask——**S9 三基准点可直接用 QRBuilder 强制构造**
  （参考 benches/qr.rs 用 `QRBuilder::new(input).ecl/mode/version().build()`）。
- `cmd/main` 已有 demo 真码（`from_string("https://example.com/").build()`），可作基准迭代的原型参考，
  但只 build 一次、不循环计时。
- 早期 wasm 微基准（docs/wasm §5.2）用的是**独立 `/tmp/bench` 模块（不入库）+ 宿主侧 `time` 多次取最小值**，
  非严格 bench，仅供选型。S9 把该朴素口径升级为**入库存量、可复跑**。
- fast_qr 官方**有 wasm 可比基线**：npm `fast_qr`（wasm-pack 构建，`fast_qr_bg.wasm`），构建链见
  `wasm-pack.sh`（nightly build-std + panic_immediate_abort + wasm-opt -Oz，docs/移植参考/wasm-绑定.md）；
  `src/wasm.rs` 以 `wasm32` 目标 + `wasm-bindgen` feature 编译。层②即与本 wasm 产物对比。

### 2.2 已列的非阻断性能建议（S5/S6 评审遗留，S9 承接盘点）
| 来源 | 建议 | 正确性风险 | S9 承接 |
|------|------|-----------|---------|
| S5 O1 | `create_auto_qr` 每掩码 `apply_mask` 全量 copy + `score` 多趟扫描，V40 下 8 轮成本可观 | **高**（主循环重构） | 不并入，单列 P2 |
| S6 评审 §3 | V40 单行 hex 分块/压缩（快照测试文件） | 低（仅测试文件） | 不属性能热点，跳过 |

> 结论：S9 承接的微优化**极少**（三基准点核心路径是 encode→structure→placement→score→build，
> 无低风险可安全优化项）；S9 主交付 = **测准基线 + 数字透明**，不做性能改写。若基准暴露某热点有

### 2.3 三基准点路径（热点对应参考性能决策）
三基准点主路径 = `QRCode::build` 编排：`select_capacity`(强制版本时直通) → `encode`(data_encoding) →
`structure`(reedsolomon 交织) → `create_fixed_qr`/`create_auto_qr`(matrix 放置 + 掩码 + score 择优)。
- **V03H/V10H/V40H 是否走自动择优**：参考 benches/qr.rs 通常**不指定 mask** → 走自动择优（8 轮 clone+score），
  这是 V40H 2.4ms 的主要成本。实现时核对参考是否固定 mask；默认按**自动择优**（不固定 mask）移植，
  与参考默认一致。
- 版本越大，放置区越大、8 轮 score 扫描越大 → V03 < V10 << V40 的耗时单调上升符合直觉。

## 3. 参考基准语义核对与关键决策

### 3.1 三基准点怎么构造（版本语义）

官方三基准点**共用同一个输入** `https://example.com/`（长度 19，全小写字母 → Byte 模式），只差版本号。
byte-H 容量表（internal constants，版本序号 = 版本-1）：V01=7 / V02=14 / **V03=24** ≥ 19 / …
故：
- **V03H**：19 字节 Byte-H 的**最小适配版本即 V03**——强制 `.version(V03)` 或自然（V03）等价；
- **V10H / V40H**：19 字节远小于这两版 Byte-H 容量（V10-H=119、V40-H=1273），**必须强制
  `.version(V10/V40)`** 才能体现大矩阵放置 + 8 轮 score 择优成本。

> **实现时核对点（含 wasm 侧）**：参考 `benches/qr.rs` 是否对三点都显式 `.version(Vxx).ecl(H)`、是否设 mask；
> **fast_qr 侧 wasm32 的 `benches`/`wasm.rs` 是否也走自动择优**需对参考源码核对（默认不指定 mask → 自动择优，
> 与 Rust 侧 benches 同构）。本方案推荐语义：
> `QRBuilder::from_string(input).ecl(ECL::H).version(Vxx).build()`（mask 留 None 走自动择优，与参考默认一致）；
> V03H 的 `.version(V03)` 显式写，保证与参考「指定版本」路径同构、可复现。
>
> **跨模型一致性红利（架构要点，层②复用）**：因 fast_qr 侧 wasm32 build 的 KEEP_LAST 已截断为 33（与
> 本仓库一致），其**跨版本算法结果应与 64 位 native 一致（同一套算法、仅位宽实现不同）**——即
> fast_qr-wasm32 对 V03H/V10H/V40H 的输出矩阵应与 fast_qr native 一致。这使层②不仅能做**计时对比**，
> 还能顺带把「MoonBit wasm 产物矩阵」与「fast_qr-wasm32 产物矩阵」做**逐位对齐**（同一算法、同一 KEEP_LAST
> 语义下应当一致），构成**正确性双验证 + 计时双验证**：既证明 MoonBit wasm 对齐了 fast_qr 的 wasm32 实现，
> 也证明两端计时在同一执行模型下可比。

### 3.2 对比口径评估（native 不可用 + wasm 形态架构 → 三层分层）

**事实 A（native 口径）**：参考 82.2/269.3/2436.2 us 是 **Rust native（64 位，KEEP_LAST=65）+ criterion** 数字；
MoonBit 的 `native` 后端需 C 编译器，当前环境不可用。直接把 wasm-gc 的 us 数与 Rust native us 数画等号是
不科学的（解释器/GC 语义差异、宿主启动开销）。

**事实 B（wasm 形态架构，决定主口径）**：本仓库是 **wasm 形态**移植（32 位 Int、KEEP_LAST=33、对全部后端
生效，§2.1）。与它语义最贴近的 fast_qr 参照物是 **wasm32 build（KEEP_LAST=33）**。因此把「对 fast_qr 的真
对比」留到 native 反而是拿「wasm 形态的 MoonBit」对「64 位 fast_qr」——比「MoonBit-wasm vs fast_qr-wasm32」
**更不同源**。fast_qr 官方本就发布 wasm 产物（npm `fast_qr` / `fast_qr_bg.wasm`，wasm-pack 构建），本仓库
README/wasm 文档的选型叙事就是「wasm 产物 + 对 fast_qr」，故层②（wasm 对 wasm）才是本仓库**真正的
主对比**，且**不依赖 C 工具链、当前环境即可落地**。

**三层分层表**：

| 对比层 | 可比性 | S9 落地 | 主/次 |
|--------|--------|---------|-------|
| **层①** MoonBit wasm-gc vs wasm（同源码后端选型） | 高（同源码语义互证，host 计时同口径） | S9-2 落地 | 选型背景（wasm §5.2 已有朴素口径，本次升级到真实 QR 路径） |
| **层②** MoonBit wasm-gc/wasm vs **fast_qr-wasm32**（检出 fast_qr 跑 `wasm-pack.sh` 产物） | **高**（同执行模型：同 wasm32、同 KEEP_LAST=33；逐位对齐 + 宿主计时） | S9-3 落地（**主口径**，不依赖 C 工具链） | **主**（本仓库定位的真对比） |
| **层③** native MoonBit vs fast_qr native（需 C 工具链环境） | 中（都 native；但本仓库 MoonBit 是 wasm 形态、KEEP_LAST=33，fast_qr native 是 64 位 KEEP_LAST=65 → 内存模型不同） | S9-4 落地（方法学 + 量级参考注记） | 次（可选，仅量级，注明口径差异） |

> **结论（相对原方案的关键修订）**：S9 核心承诺升级为「在**当前环境**给出 MoonBit wasm（wasm-gc/wasm）
> 对 **fast_qr-wasm32** 的**逐位对齐 + 计时双验证**（层②，主口径）」；native MoonBit vs fast_qr native
> **降为可选方法学注记**（层③，需工具链环境、注明内存模型差异、仅量级参考，非主口径）。跨后端选型
> （层①）保留为背景，避免与 wasm §5.2 语义重复。参考 82.2/269.3/2436.2 us 一律标注「64 位 native」并
> 提示口径（§1 已加注）。

### 3.3 决策 D14：基准载体 = `cmd/bench`（不入库或按需入库，见 §4.1）

- MoonBit 无 criterion；最贴近参考「重复迭代 + 取中/最小」的 = 一个**可执行命令**循环 build N 次 +
  宿主侧计时。放 `cmd/bench/`（`pkgtype(kind:"executable")`）与 `cmd/main` 并列，语义清晰、可
  `moon run cmd/bench --target <后端>`。
- 该载体**同时喂层①与层②**：层① = `moon run cmd/bench --target wasm-gc/wasm`；层② = 同一宿主计时脚本
  （`scripts/bench.sh`）再驱动 fast_qr-wasm32（JS/npm 宿主）产物跑三基准点并取相同口径数字。
- 不空建顶层 `bench/`（roadmap「出现信号再拆」，现仅 1 入口 + 计时脚本，不构成多包基座）。

### 3.4 决策 D15：计时口径（宿主侧，对齐 wasm §5.2）

基准命令内部不内置纳秒钟（跨后端 host 计时更一致），由**宿主**（`time` / 计时脚本）对
`moon run cmd/bench --target <后端>` 整程计时；命令内用 `@time`（若 MoonBit 提供）仅作粗略节拍，主口径靠
宿主重复 run 取多次最小值（剔除冷启动，wasm §5.2 已用此法）。迭代数 N 由命令行参数传入（V40 大、需少
迭代；V03 小、需多迭代，避免单次 <1ms 计时噪声）。**fast_qr-wasm32 侧（层②）用同一宿主计时口径**：
JS/npm 宿主重复调用 wasm 产物、取多次最小，与 MoonBit 侧数字同口径可比。

### 3.5 优化承接策略（D16）：S9 只测基线，不做主循环改写

S5 O1（8 轮 clone→就地翻转）等正确性敏感重构**单列 P2 专项**，不进 S9。S9 只承接「把 `size`/版本等
循环外提」这类零风险等价改写（若基准暴露），并在改写前后各测一次做佐证，回归 109 全绿 + 快照零差异。

### 4.1 cmd/bench 是否入库？
- **建议入库**（与 `cmd/main` 并列），作为「可复跑基准」常驻，供后续优化反复对比——这与 S9「M3 性能与
  分发基线」吻合。若团队倾向「基准不入 main 产物面」，可放 lib 下 `*_bench_test.mbt`（core 参考机制），
  但该机制属 P2 待办、现无基座，故**首选 cmd/bench** 最小可行。
- 层②的 fast_qr-wasm32 对比**复用同一载体口径**：检出 fast_qr 跑 `wasm-pack.sh` 产物（不放本仓库入库，
  作为外部参照物），由 `scripts/bench.sh`（或按需的 JS 驱动脚本）用与 MoonBit 侧相同的宿主计时口径跑，
  **不必等 native 环境**。
- 回滚：`git revert` 即复原；基准包不影响公共 `.mbti`（非 lib 公共符号）。

### 4.2 风险与回滚
- **风险低**：S9 = 新增独立基准命令 + 宿主计时脚本 + 文档，不触碰任何公共 API / 内部管线 / 快照对齐。
- 需盯的 3 点：① 基准强制版本语义必须与参考 benches/qr.rs 一致（§3.1 实现时核对）；② **fast_qr-wasm32
  三基准点是否走自动择优需对参考源码核对**（§3.1），确保层②逐位对齐口径正确；③ 计时口径跨后端/跨语言
  要统一（多次取最小、剔冷启动），否则数字不可比。
- **回滚**：任一文件 `git revert`；基准包不入 `.mbti`，不影响对外接口。

## 6. 汇总

1. **读了代码与文档**：盘点 S8 落地后 lib/internal/cmd/main 全貌、公共入口（QRBuilder 可强制版本）、
   可用后端（wasm-gc/wasm、无 native）、**内存位宽事实（MoonBit Int 32 位、KEEP_LAST 取 Rust wasm32 分支
   33 项、对全部后端生效 → 本仓库是 wasm 形态）**、已列性能建议（S5 O1 等）、fast_qr 官方 wasm 产物链
   （npm `fast_qr` / `fast_qr_bg.wasm` / `wasm-pack.sh`）。
2. **读了 roadmap 并评估 S9**：S9 = 移植三基准点 V03H/V10H/V40H（输入固定、强制版本 + ECL H）、
   透明对比（无硬门槛）、收敛 M3。核心障碍 = **native 不可用**，故对比**三层分层**：层①跨后端选型
   （wasm 内可落地）+ **层② MoonBit-wasm 对 fast_qr-wasm32（主口径，同执行模型、不依赖 C 工具链、当前
   环境可落地）** + 层③ native 对比（可选方法学量级注记、需工具链）。口径透明即可。
3. **S9 定方案**：落地 `cmd/bench` 基准命令 + 宿主计时脚本（D14/D15），**宿主计时口径同时喂层①与层②**
   （检出 fast_qr 跑 wasm-pack 产物、同一脚本），wasm-gc/wasm 与 fast_qr-wasm32 跑出**逐位对齐 + 计时**
   双验证数字；只测基线、不并入主循环重构（D16，S5 O1 单列 P2）；记录 + README/roadmap 治理。回归
   109 全绿 + 快照零差异即安全。

**S9 后续（实现阶段首个动作）**：在具备 MoonBit 工具链环境建 `cmd/bench` + `scripts/bench.sh`，
按参考 benches/qr.rs 核对三基准点强制版本语义（含 wasm 侧自动择优核对）后跑 wasm-gc/wasm 基线；再检出
fast_qr 跑 `wasm-pack.sh` 产物，用同一宿主计时跑 fast_qr-wasm32 三点并做逐位对齐（层②，主口径）；可选在
装 C 工具链 + fast_qr 的环境补 native 对比（层③，量级注记）。S9 达成即 roadmap M3（性能与分发基线）收口。
