# 跨语言重写评估

> **状态**：现行　｜　日期：2026-09-14　｜　索引：[docs/README-导航与索引.md](../../../README-导航与索引.md) §7

本文回答一个问题：如果要用其他语言重写 fast_qr，应当如何开始？基于对仓库源码的逐模块分析给出结论与可执行路线。

## 1. 重写前的现实评估：值得重写吗

fast_qr 的性能优势几乎全部来自 Rust 特定手段（编译期常量折叠、固定大小数组、零成本抽象、LTO）。重写的收益取决于目标场景：

| 目标场景 | 重写是否有意义 | 理由 |
|------|------|------|
| 为 Python/Java/Node 等提供原生绑定 | 有意义 | 目前只能通过 WASM 或调用 Rust 工具链，C ABI 核心可让所有语言低成本接入 |
| 服务端微服务（Go/Java 生态） | 有意义 | 消除跨语言 FFI 复杂度，团队可维护性优先 |
| 浏览器零 WASM 依赖 | 部分有意义 | 纯 TS 实现便于调试与审核，但性能上限显著低于现有 WASM 路径 |
| 仅为了"学 Rust 之外的语言" | 有意义 | 本项目管线清晰、测试完备，是理想的移植练习对象 |
| 想比 Rust 版更快 | 意义有限 | 核心查表算法已接近内存带宽上限，C/Zig 至多打平或小幅领先（SIMD 对本 workload 收益小，数据量仅 KB 级） |

## 2. 被重写对象的真实复杂度

按依赖序统计核心管线（不含 convert/wasm/测试）：

| 模块 | 行数 | 移植难度 | 说明 |
|------|------|------|------|
| `version.rs` | 819 | 低（机械） | 容量选择是纯表驱动 match，可脚本化从 Rust 源码转译成任意语言的表 |
| `hardcode.rs` | 412 | 低（机械） | 分组表/格式信息表/生成多项式，全是常量 |
| `module.rs` + `qr.rs` | 470 | 低 | Module = u8 打包，QRCode = 固定数组 + size |
| `encode.rs` + `compact.rs` | 426 | 中 | 位操作需仔细对齐（大端序写入、KEEP_LAST 掩码表） |
| `polynomials.rs` | 164 | 中 | GF(256) 除法 + 块交织，索引技巧多（固定 255/5430 大小的栈数组） |
| `default.rs` | 262 | 中 | 6 类功能图案的坐标逻辑 |
| `placement.rs` | 141 | 中 | 之字形遍历跳过第 6 列、双向 y 遍历 |
| `datamasking.rs` | 174 | 中 | 8 个掩码函数，掩码 5/6 共用偏移表技巧 |
| `score.rs` | 201 | 高 | 4 条评分规则 + ISO N3 的 11 位滚动窗口 + quiet zone 语义 |
| `ecl.rs` + `lib.rs` + `helpers.rs` | 215 | 低 | 枚举与输出工具 |

**核心管线约 3280 行，无第三方依赖**。convert（SVG/PNG）与 wasm.rs 共约 1170 行，属于外围，可按需重写或用目标语言生态替代。

## 3. 候选语言对比

评估维度：性能上限、内存控制、跨语言绑定能力、WASM 支持、开发者体验。

### C（C99/C11）
- 性能：天花板最高，`[177*177]` 固定数组、位操作、查表全部直译
- 绑定：C ABI 是事实标准，Python(ctypes/cffi)、Node(node-addon-tools)、Java(JNI/Panama)、Go(cgo)、.NET(P/Invoke) 全部一等支持
- WASM：clang `--target=wasm32` 或 Emscripten 成熟
- 风险：内存安全需自查（但本 workload 全是栈/静态分配，风险面小）；CI 矩阵维护成本高
- 先例：Nayuki 的 qrcodegen（C + 多语言移植版）验证了此路线可行

### Zig
- 性能与 C 持平；`comptime` 可把 Rust 的 const fn 容量 match 表达得更自然（编译期生成表）
- 内置 `wasm32-freestanding` 目标、`zig cc` 一键交叉编译、可自动导出 C 头文件
- 风险：语言未到 1.0，语法仍在变动

### Go
- 性能：预计比 Rust 慢 10-20%（无 LTO 到同等程度、GC 管理大数组需用 `[31329]byte` 值类型注意逃逸）
- 优势：`go:wasmexport`、单二进制部署、并发批量生成场景天然占优
- 位操作与查表可直译；固定数组传参注意用指针

### C++（C++20）
- 性能与 C 同级，`std::array<Module, 31329>` 直译 Rust 结构，`constexpr` 可替代 const fn
- 风险：构建生态碎片化；对 QR 这种小工具收益有限

### Java/Kotlin (JVM) 与 C# (.NET)
- 性能：JIT 后可达 Rust 的 60-80%；黑块用 `byte[31329]`、避免装箱即可
- Java 22+ 的 Vector API 对本场景收益小；.NET 的 `Span<T>`/`stackalloc` 表达力好
- 适合企业 SDK 场景，通用性弱于 C ABI 路线

### TypeScript（纯 JS 实现）
- 性能：比 WASM 慢一个数量级，但 QR 生成单次本就在百微秒级，前端场景通常够用
- 优势：零二进制、可审计、包体最小（无 wasm 文件）

### 结论
- **目标 = "一个核心，处处可用"** → 选 **C 或 Zig**（推荐 C，参照 qrcodegen 先例；团队愿意承担语言演进风险选 Zig）
- **目标 = 服务端/云原生** → 选 **Go**
- **目标 = 企业 JVM/.NET 内部库** → 选 Java 或 C#
- **目标 = 纯前端零依赖** → 选 TypeScript（甚至可从 WASM 版导出的矩阵做 fuzz 对照）

## 4. 重写启动路线图（7 步）

以下顺序按"风险递增"排列，每步完成后都有可验证的产出。

### 第 1 步：锁定正确性基线（1-2 天）
- 从 `src/tests/version.rs`（3876 行黄金数据）、`tests/polynomials.rs`（1168 行）提取期望值表，转成目标语言测试数据（可写脚本从 Rust 源码自动转译）
- 用本机或 CI 跑一遍 `fast_qr`，对 40 版本 x 4 ECL x 3 模式生成矩阵 JSON 快照，作为跨实现回归基准
- 建议同时引入 Nayuki qrcodegen 作为第二参照实现，三者交叉验证

### 第 2 步：移植常量表（1-2 天）
- `hardcode.rs` 的 `ecc_to_groups`（u32 位打包的两个 (count,size) 对）、`ecm_to_format_information`、`get_polynomial`
- `version.rs` 的容量 match → 目标语言的静态表
- `polynomials.rs` 的 LOG/ANTILOG 256 项表
- 验收：目标语言测试全部通过，此步骤零算法风险

### 第 3 步：搭建核心数据结构（1 天）
- `Module`：1 字节，bit0 = 明暗，bit1-3 = 类型号（Data=0/Finder=1/.../Empty=7；判别值按 `序号 << 1` 打包，详见 [Module](./module.md)）
- `QRCode`：固定 31329 字节数组 + `size` 字段；提供 `index(row)` 切片语义
- `CompactQR`：预分配字节数组 + `len` 位计数器，实现 `push_bits`/`push_u8`/`fill`（注意 `push_bits` 的大端序与跨字节拼接逻辑，`src/compact.rs:177-208`）

### 第 4 步：自底向上实现管线（3-5 天）
1. `encode`：三模式（Numeric 三位一组 10 bit / Alphanumeric 两字符 11 bit / Byte 直拷）+ terminator + 8 位对齐 + `[236,17]` 填充
2. `polynomials::division`：GF(256) 综合除法（查表乘法）
3. `polynomials::structure`：分块纠错 + 数据/纠错码字交织（`g1`/`g2` 两组）
4. `default`：finder/timing/dark module/alignment/version info/format 预留
5. `placement`：之字形放置（`0..6` 与 `7..N` 拼接、步长 2、y 方向交替）
6. `datamasking`：8 个掩码
7. `score` + `place_on_matrix` 主循环

### 第 5 步：性能验证（1-2 天）
- 移植 `benches/qr.rs` 的三个基准点：V03H / V10H / V40H，输入固定为 `https://example.com/`
- Rust 基线：82.2us / 269.3us / 2436us（来自 README）
- 重点排查三处性能陷阱：
  1. 固定数组是否逃逸到堆（Go/Java 尤其注意）
  2. 掩码 8 轮循环是否复用缓冲而非反复分配
  3. 评分列扫描是否复用栈缓冲（对应 `src/score.rs:156` 的优化）

### 第 6 步：输出层与绑定（2-4 天）
- SVG：纯字符串拼接（`Shape` 6 种 + 自定义函数），直译 `convert/svg.rs`
- PNG：Rust 版走 resvg 栅格化；重写版建议直接像素级绘制位图再编码 PNG（QR 是纯几何图形，跳过 SVG 栅格化反而更快、依赖更少）
- 绑定：C 路线写各语言薄壳；Go 路线直接 `go:wasmexport` 或纯库使用

### 第 7 步：工程化（1-2 天）
- CI 矩阵对齐 `.github/workflows/rust.yml`：default / svg / image / wasm 四种 feature 组合
- fuzz：对 `push_bits` 与 `encode` 输入做模糊测试（Rust 版有对应测试覆盖思路）
- 体积：C/Zig 路线用 `wasm-opt -Oz` 对齐；Go 路线注意 `wasm_exec.js` 体积劣势

**总工期估算**：单人全职 C 路线约 3-4 周（含绑定）；Go 约 1-2 周；TypeScript 约 1 周（性能上限低）。

## 5. 最快可用重写路径（约束：保留原 API 与架构）

第 4 节是通用路线图。本节在两条硬约束下给出落地排期：**最快达到可用**、**保留原 API 与架构**。

### 5.1 两条约束的可度量定义

"可用"与"保留"必须是可验收的，否则排期无法收敛：

**验收门槛 1 — 正确性**：与原版生成的矩阵逐位一致。对齐范围：40 版本 x 4 ECL x 3 模式的代表性内容（含 V1 最小、V40 最大、V7+ 版本信息区、跨第 6 列跳过逻辑）。

**验收门槛 2 — API 同构**：公开面一一对应，来自 `src/lib.rs:75-108` 的导出清单：

| 原 API（Rust） | 保留要求 |
|------|------|
| `QRBuilder::new(input).mode/ecl/version/mask().build()` | 同名构造器 + 5 个链式方法 + build 返回（QRCode, 错误） |
| `QRCode { data: [Module; 31329], version, ecl, mask }` | 同字段结构体，`to_str()`/`print()` 保留 |
| `ECL`/`Version`/`Mode`/`Mask`/`Module`/`ModuleType` | 枚举值与判别值一致（ModuleType 保持 `<<1` 打包） |
| `SvgBuilder.shape/margin/...().to_str/to_file` | Builder 链式语义保留 |
| `ImageBuilder.fit_width/fit_height/to_pixmap/to_file/to_bytes` | 方法名保留，实现可推迟（见 5.6） |
| JS `qr(content) -> u8[]`、`qr_svg(content, options) -> string` | 同名同返回形状（失败返回空数组） |
| JS `SvgOptions` 链式配置 | 全部字段与方法保留 |

**验收门槛 3 — 架构同构**：核心管线各模块（encode/compact/polynomials/hardcode/version/ecl/module/default/placement/datamasking/score）同名同边界；单向依赖 `encode → compact → polynomials → placement → qr` 不变；测试文件与 `src/tests/mod.rs:1-11` 同名对应。

### 5.2 策略选择：为什么是"机械翻译 + 黄金测试"，而不是"按规范重新实现"

重写的最大成本是正确性收敛，速度由验证策略决定。两条路线对比：

| 路线 | 做法 | 收敛速度 | 风险 |
|------|------|------|------|
| 按规范重新实现 | 只参考规范，测试自己写 | 慢：会重新踩一遍原作者的坑（第 6 节的 8 个高危点全部命中），每个坑平均消耗半天到一天 | 高 |
| 机械翻译 + 黄金测试 | 逐文件翻译，断言直接抄原测试 | 快：算法已确定、期望值已存在（`tests/version.rs` 3876 行、`tests/polynomials.rs` 1168 行、`tests/structure.rs` 489 行全是现成期望值表），翻译即架构保留 | 低 |

"保留原 API/架构"约束恰好排除了"重新设计"的空间，使机械翻译成为合法且最优的策略。

### 5.3 核心加速器：双层验证（快照对齐 + 黄金数据）

**第 0 天先建快照工具**（Rust 侧约 30 行，作为重写工作的第一步产出）：

```text
输入: (content, ECL, 可选 version) 列表
输出: JSON，每个条目含 31329 字节矩阵 + 最终 version/ecl/mask 选择
```

快照集设计（约 60 个条目即可覆盖全部代码路径）：

- 4 个 ECL x 3 模式各 3 个版本（低/中/高）= 36 个
- V7/V14/V26/V32（版本信息区触发点）各 1 个 = 4 个
- 边界：V1-L 最短内容、V40-H 满容量内容 = 2 个
- 指定 mask 与指定 version 的 API 路径 = 若干

**双层验证的分工**：

1. **快照对齐**（端到端）：重写版读同一 JSON 逐位对比。任何模块的翻译错误都会在此暴露，一次运行覆盖全部管线，这是比"逐模块单测通过再联调"快 2-3 倍的关键。
2. **黄金数据**（单元）：快照失败时，用抄自原测试的期望值表收缩定位到具体函数。断言数据从 `src/tests/*.rs` 直接转译，零编写成本。

### 5.4 架构同构映射（以 Go 为例，其他语言同构替换）

| 目录/模块 | Go 对应 | 翻译要点 |

| `src/compact.rs` | `compact.go` | KEEP_LAST 表 65 项（64 位目标）；`push_bits` 大端序逻辑逐行对照 `src/compact.rs:177-208` |

### 5.5 分天排期（Go 路线，7 个工作日；C/Zig 对照）

每天有明确验收标志，任一天超期说明该模块有理解偏差，回退用黄金数据收缩：

| 天 | 内容 | 验收标志 |
|----|------|------|
| D0（0.5 天内完成） | 快照工具 + 快照集生成；测试脚手架；表提取脚本 | 60 个快照 JSON 生成；`version`/`hardcode` 表测试全绿 |

| D2 | polynomials（division + structure） | `tests/polynomials.rs` 1168 行期望值全绿；`tests/structure.rs` 全绿 |
| D3 | default 图案 + placement 数据放置 | Byte 模式固定 mask 出第一个码，与快照对比仅掩码差异 |
| D4 | datamasking 8 掩码 + score 4 规则 + 择优 | V1-V10 全部 ECL 快照逐位对齐（最难点，预留一整天） |

C/Zig 路线同表推进，工期约 2-2.5 周：表提取与管线翻译各多 2-3 天（手动内存布局、头文件、构建脚本），绑定层多 3-4 天。

### 5.6 范围裁剪：第一版保留什么、推迟什么

保留 API 约束下，公开面全部保留，但内部实现允许分两期：

| 项 | 第一版 | 推迟理由 |
|----|------|------|
| 核心管线（encode→score 全部模块） | 完整翻译 | 可用性的本体 |
| SVG 输出（6 种 Shape + Command） | 完整 | 纯字符串拼接，成本半天 |
| PNG 输出（ImageBuilder） | 方法名保留，内部返回未实现错误或用目标语言原生 PNG 编码 | 原版走 resvg SVG 栅格化链路重；直接位图绘制 + PNG 编码是第二期更快更轻的替代（见第 4 节第 6 步） |
| WASM（qr/qr_svg/SvgOptions） | 完整 | 236 行胶水；构建链先用标准 wasm-pack，nightly `-Z build-std` + `wasm-opt -Oz` 体积优化推迟 |
| 终端输出 to_str/print | 完整 | 20 行 |
| 性能优化（const 折叠、逃逸分析调优） | 推迟到快照全绿之后 | 正确性未收敛前做优化会干扰定位 |

### 5.7 完成定义

满足以下全部条件即可宣布"最快可用重写完成"：

1. 60 个快照 100% 逐位对齐（正确性门槛）
2. API 映射表（5.1）全部条目存在且签名同构（API 门槛）
3. 模块目录与依赖方向对照检查通过（架构门槛）
4. 三基准点可跑通并给出与 Rust 版的对比数字（性能透明度；数字本身在第一期不设门槛）
5. 黄金数据测试（version/polynomials/structure/compact/encode）作为常驻测试集保留

## 6. 重写中的高危细节（来自源码注释与实现的实证）

这些点在"按规范重写"时最容易做错，fast_qr 的实现包含规范未明说的工程决策：

1. **评分的 quiet zone 语义**（`src/score.rs:84-100`）：ISO N3 规则中，finder 图案相似串两侧需有 4 个浅色模块。fast_qr 用"行首/行尾补 0 位"模拟符号边缘外的 quiet zone，且两侧都浅的图案会命中两个窗口、计两次 40 分。重写版必须用快照测试对齐，而非仅凭规范实现。
2. **列评分必须在掩码后进行**（`src/placement.rs:100-104` 注释）：若先转置再掩码，所有垂直惩罚会变成常量，列永远影响掩码选择。这是该项目真实修过的 bug。
3. **2x2 方块评分的模块类型门槛**（`src/score.rs:60-64`）：相邻模块含功能模块时该方块不计分，连续性计数器归零。规范未明说，属实现决策。
4. **掩码 5/6 的偏移表**（`src/datamasking.rs:94-139`）：以 6x6 网格循环 + 固定偏移数组实现 `(x*y)%2 + (x*y)%3` 判定，避免逐像素乘法。
5. **交织数组的固定尺寸**（`src/polynomials.rs:106-119`）：`[u8; 5430]` 与 `[u8; 255]` 栈数组硬编码上限（MAX_ERROR=30, MAX_GROUP_COUNT=81, MAX_DATABITS=3000），重写时需按目标语言栈容量调整。
6. **WASM 侧 KEEP_LAST 表截断到 33 项**（`src/compact.rs:52`）：wasm32 下 usize 为 32 位，重写目标语言若是 64 位平台需保持表项与位宽一致。
7. **Format 信息区的占位→覆盖时序**（`src/default.rs` 先写入占位 Format 模块，`src/placement.rs` 掩码择优后再写入真实格式信息）：重写时若先写真实值，评分会把 Format 区当作数据参与，掩码选择与原版不一致。快照对齐可立即暴露此错误。
8. **u8 算术的回绕与移位语义**：`Module` 的类型判别值全部左移 1 位（`src/module.rs:4-41`），GF(256) 乘法用 `(a + b) % 255` 的 alpha 幂加法（`src/polynomials.rs:83`）。目标语言需显式使用 8 位无符号类型与无符号取模，强类型语言（Java/C#）的默认 int 会改变溢出行为。

- `convert/image.rs`：resvg 依赖链很重，重写版直接位图绘制更简洁（见第 4 节第 6 步与 5.6 裁剪表）
