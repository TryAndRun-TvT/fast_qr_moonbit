## 2. 发现的问题与修复

### 2.1 【已修复·真实 BUG】`is_qr_alphanumeric` 检查 `38`（`&`）而非 `42`（`*`）

- **现象**：`is_qr_alphanumeric` 的特判字符分支为 `32, 36, 37, 38, 43, 45, 46, 47, 58`，
  其中 `38` 是 `'&'`（**非** QR alnum 合法字符），而合法字符 `'*'`（ASCII **42**）不在列表中。
- **后果**（两条错误路径）：
  1. **输入含 `'*'`**：`best_encoding` 对 `"HELLO*WORLD"` 返回 Byte(2) 而非 Alnum(1)。
     输出仍是正确二维码，但编码效率降低（Byte 模式用 8 bit/字符 vs Alnum 模式平均 5.5 bit/字符）。
  2. **输入含 `'&'`**：`best_encoding` 对 `"HELLO&WORLD"` 错误返回 Alnum(1)。
     后续 `encode_alphanumeric` 调用 `ascii_to_alphanumeric(b'&')` 时会命中 `abort()` → **程序崩溃**。
- **与已修 bug 同源**：S3 记录 §5 已记录了 `ascii_to_alphanumeric` 早期把 `*`(42) 误写为 38
  并修复。但修复只覆盖了映射表侧，**未同步到判定函数 `is_qr_alphanumeric`**，形成同源漏网。
- **修复**：`encode.mbt` 中 `is_qr_alphanumeric` 的 `b == 38` 改为 `b == 42`。
- **回归测试**：
  - `is_qr_alnum` 测试补 `assert_eq(is_qr_alphanumeric(b'*'), true)` 与
    `assert_eq(is_qr_alphanumeric(b'&'), false)`；
  - 新增 `best_encoding_star_ampersand` 测试：`"HELLO*WORLD"`→1、`"HELLO&WORLD"`→2、
    `"5*9"`→1。
- **影响面**：仅 internal/data_encoding 的判定函数行为修复，公共 `.mbti` 面不变。
  测试 63→64（+1 新测试 + 既有测试补断言）。

## 3. 已确认正确的设计点（维持现状）

| 决策 / 实现 | 评审结论 |
|-------------|---------|
| `cci_bits` 归 `capacity.mbt`（D1），三分支 if/else 不建表 | 与 `data_bits` 同叶保持「容量/字符计数」聚合；Byte 只在 V10 升 16、V27 不再涨，语义与参考一致 ✓ |
| `encode.mbt` 三模式 + terminator/pad/fill 一次全落（D2）| 三个编码器各自独立可验证，不需要矩阵即可黄金对齐；避免 S6 返工 ✓ |
| `encode` 返回的 CompactQR 数据经 fill 铺满 max_bytes，S4 取 data[0..data_codewords] 作 structure 输入 | 含 [236,17] 占位的完整数据码字区 = QR 规范要求；S4 端需按 data_codewords(ecl,v) 切字节 ✓ |
| `ascii_to_alphanumeric` 修正后含 `42 => 39`；`abort()` 兜底 | 非法 Alnum 字符在 encode 阶段即失败，便于定位 ✓ |
| `select_capacity` 返回 (mode_idx, ecl_idx, version_idx) 三元组 | 符合 internal 以序号传递的依赖规则；S4/S6 QRBuilder 消费此三元组 ✓ |
| `QRCodeError` 两个变体在容量选择路径可达构造 | 解除 S1 的 `unused_constructor` 推迟，满足 --deny-warn ✓ |
| lib 首次 import internal（无环）| `data_encoding` 与 `constants` 的 import 在 B8 使用路径上实际消费，无 unused_package ✓ |
| 越界「静默回退」策略 | internal 受控调用方 + encode 前 capacity 由 select_capacity 保证 ✓ |
| bitbuffer `push_bits` 收尾用 `+`（S1 记录 §3.4）| 已确认字节为 0（该位置从未写入），`+` 与 `\|` 语义等价；属风格偏好非 bug ✓ |

## 4. 后续注意点（记录项，非阻断）

### 4.1 用户显式指定 Numeric/Alnum 模式但数据不匹配
`select_capacity` 不验证用户指定的 mode 是否与实际数据匹配（fast_qr 同样如此）。
如 `Some(Mode::Numeric)` + 含字母的输入会静默产出错误编码。
建议：S6 公共 QRBuilder 落地时在 `build()` 入口做 mode×content 兼容性校验并返回错误。

### 4.2 encode() 不校验数据是否超出指定版本的 data_bits
直接调用 `encode(input, ecl, mode, version)` 若 input 过大，会静默溢出到错误输出
（MoonBit 因 push 按需扩容不会 panic，fast_qr 的 usize 相减会 underflow panic）。
建议：S4 接入时在 create_matrix 入口复用 `select_capacity` 做容量断言。

### 4.3 `fill()` 前置条件 `len % 8 == 0` 仅文档声明、不运行时校验
encode 管线在 pad_to_8 后调用保证成立；独立调用 fill() 时可能产生非预期输出。
建议：保持现状（内部受控），不必加断言。

### 4.4 `structure()` 每次分配 5430 字节缓冲（S2 记录 §3.5 遗留）
多数版本实际用不到此大小。S7 产码/封装时若测到分配热点可按需优化。

## 6. 下一步
S3 的 encode 位流已是 S4 `structure` 的输入契约。下一步建议：
1. S4 先落 `internal/matrix` 的功能图案与放置（B9 前半），此时可用 encode 产物做
   `structure(data[0..data_codewords])` 端到端验证（M1 首码快照对齐）；
2. 在 S4 消费 encode 输出时，注意 encode 的 data 数组已含 [236,17] fill 占位，
   须按 `data_codewords(ecl,v)` 切取前 N 字节传 structure。
